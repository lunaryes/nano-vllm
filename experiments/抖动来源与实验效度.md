# 抖动来源与实验效度：离线推理能否验证「流式平滑性」

> 触发于 2026-10-14 的追问：「混合调度除了长序列，还有一个目的是不是流式对话的平滑性？在当前这种离线推理中，只有抢占重 prefill 会导致 TPOT 抖动吗？其他情况测不出来？」
>
> 数据来自 B 组三场景 r1（`results/b3_*.json`），分析脚本 `b4_jitter_decomp.py`，原始表 `results/b4_jitter_decomp.md`。

---

## 结论（先说三条）

1. **平滑性确实是混合调度的目的之一**，而且在我们这套实验里它是**唯一真正兑现的收益**（吞吐是 0.99×，见 B5/C0）。
2. **抖动不需要抢占。** 实测两版抢占均为 **0**，main 依然有 88 / 88 / 66 段停顿，占墙钟 **14.6% / 35.6% / 28.5%**。产生抖动的是**相位分离**（prefill 步里 decode 完全停摆），与抢占无关。
3. **离线推理的抖动源有 4 类，3 类可测、1 类结构性缺失**（运行中新请求的到达过程）。

---

## 一、混合调度的两个目的

| 目的 | 机制 | 在我们实验里的兑现情况 |
| :--- | :--- | :--- |
| **① 吞吐** —— 避免 prefill / decode 互相等待，提高 GPU 利用率 | 同一步里 prefill 的算力填满 decode 的空隙 | **未兑现**（交替配对 0.991×，三个方向相反的力互相抵消，见 C0） |
| **② 平滑性** —— decode 不被长 prefill 饿死 | 长 prompt 切成 chunk，与 decode 混在同一批 | **兑现**（ITL max 降至 1/20，见下） |

在 nano-vllm 的语境下，**②才是主战场**。原因见下节。

---

## 二、抖动的完整来源

「某个正在 decode 的 seq，为什么某一步拿不到 token」——只有四种可能：

| # | 来源 | 机制 | 触发条件 | 离线可测？ |
| :--- | :--- | :--- | :--- | :--- |
| 1 | **相位分离** | main 的 `schedule()` 只要 waiting 非空就整步做 prefill，**decode 段完全不执行** → 已在 decode 的 seq 集体停摆 | waiting 非空（即存在排队积压） | ✅ **可测，且是主因** |
| 2 | **混合步自身成本** | V1 的混合步耗时 = `T_prefill(chunk) + T_decode`，该步的 ITL 被拉长 | 有 chunked prefill | ✅ 可测（V1 的残余抖动） |
| 3 | **抢占重 prefill** | 池不足 → `preempt()` → 重入时哈希失效、整段重算 768~1025 token | 池 < 峰值需求 | ✅ 可测，但**可被锁池归零** |
| 4 | **新请求到达** | 在线服务里新用户的长 prompt 随时到达，打断正在输出的对话 | 有到达过程（泊松/突发） | ❌ **结构性缺失** |

**用户的假设只覆盖了第 3 类。** 实测证明第 1 类才是本实验的主要抖动源，且它的触发条件（waiting 非空）比抢占**宽松得多**——只要请求数超过并发上限，就必然发生。

### 2.1 代码级机制：相位分离的唯一根源

`nanovllm/engine/scheduler.py`（main 分支），`schedule()` 的全部要害只有一行：

```python
# ---- prefill 段：只处理 waiting[0]，切 chunk 填满 budget ----
while self.waiting and len(scheduled_seqs) < self.max_num_seqs:
    seq = self.waiting[0]
    remaining = self.max_num_batched_tokens - num_batched_tokens
    ...
    seq.num_scheduled_tokens = min(num_tokens, remaining)
    ...

if scheduled_seqs:
    return scheduled_seqs, True        # ← 一旦 admit 到任何 seq，立刻返回
                                       #   decode 段在本步【完全不执行】

# ---- decode 段：只有 prefill 段一个都没 admit 到时才会走到 ----
while self.running and len(scheduled_seqs) < self.max_num_seqs:
    ...
return scheduled_seqs, False
```

三个直接推论：

1. **每步只 prefill 一条 seq 的一个 chunk**（`remaining` 在第一轮就被填满归零）。
   长 prompt ≈ 4700 token ÷ budget 1024 = **5 个连续步**才 prefill 完一条。
2. **池满时 `can_allocate` 返回 -1 → break → prefill 段为空 → 才走 decode**。
   所以 main 的步序列形状**由「池何时腾出空位」决定**：

   ```
   [35 步纯 prefill][N 步 decode][5 步 prefill][M 步 decode][5 步 prefill]…
   ```

   35 = 初始一波 admit 7 条 × 5 chunk；之后的 5 步块 = 每完成一条 seq 就腾出空间 admit 一条新的。
3. V1 的顺序恰好相反：**`running` 段先跑**（decode 每步 1 token / chunked prefill 吃剩余预算），waiting 段再补 —— **同一步内 prefill 与 decode 并存**。

### 2.2 「ITL = decode 步时长」为什么不成立

ITL 的构成是：

```
ITL(第 k 个 token → 第 k+1 个 token)
   = Σ (这两次产出之间所有调度步的墙钟)
  ≠ 单个 decode 步的执行时长
```

main 的 decode 步本身只有 **~25 ms**（long 场景实测），这个说法**没错**。但两次产出之间插了 **35 个 55.8 ms 的纯 prefill 步**：

```
ITL = 35 × 55.8 + 25 ≈ 1978 ms        （实测 ITL max = 1984 ms，自洽）
```

> **不是 decode 变慢了，而是 decode 那一步根本没被调度。**
> 该 seq 全程待在 `running` 里、KV 块没被释放、**从未被抢占**——它只是连续 35 次没被选中。

所以「没有抢占 → decode 一定平滑」的推理断在了一个隐含前提上：
**它默认了"每一步都在做 decode"**。而 main 在 prefill 段里一步 decode 都不做。

### 2.3 正确的平滑条件（比「无抢占」强得多）

| 条件 | 含义 | 本实验是否满足 |
| :--- | :--- | :--- |
| **无抢占** | 池够用，resident 不超容 | ✅ 满足（抢占 = 0） |
| **无排队积压**（waiting 为空） | 没有"还没 admit 的请求" | ❌ **不满足**（N = 96 ≫ 并发 7） |

**平滑真正需要的是后者。** 只要 waiting 非空，main 就会反复整步 prefill，decode 被反复搁置——这与池够不够、有没有抢占**完全无关**。

反过来，如果 waiting 恒空（例如 N ≤ 并发上限），main 会全程连续 decode，那时确实平滑——**这也正是"没有抢占就平滑"能成立的那个特例**。但那种配置下实验也测不到任何信号（见 §四）。

### 2.4 「相位分离下 TPOT 很好」这个直觉错在哪

这个直觉是**对的，但用错了对象**。它默认了：

> 「所有 seq 在同一时刻进入同一相位」—— 一起 prefill，一起 decode。

若真如此，那么相位 1 里没有任何 seq 在 decode（谈不上 TPOT），相位 2 里全是 decode（TPOT 完美），相位分离确实无害。

**但 main 的 admit 是严格串行的**，因为 budget 一步只装得下一条 seq 的一个 chunk：

**long 场景实测（前 46 步，池 152，并发 8）**

| 步号 | 1 | 2 | 3 | 4 | 5 | 6 | … | 40 | 41 | 42 | … |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: | :--- | ---: | ---: | ---: | :--- |
| prefill tok | 1024 | 1024 | 1024 | 1024 | 606 | 1024 | … | 627 | 0 | 0 | … |
| decode tok | 0 | 0 | 0 | 0 | 0 | 0 | … | 0 | **8** | **8** | … |
| 步耗时 | 43.3 | 53.0 | 60.3 | 69.0 | 49.2 | 49.7 | … | 52.4 | **25.8** | **25.8** | … |
| 相位 | P | P | P | P | P | P | … | P | **D** | **D** | … |

- 步 1~5 = seq1 的 5 个 chunk（1024×4 + 606 = 4700）→ **seq1 在步 5 产出第一个 token**
- 步 6~10 = seq2 的 5 个 chunk → 此刻 seq1 已在 `running`，**但一步都轮不到**
- 步 11~40 = seq3~seq8 同理
- 步 41 = 池满、`can_allocate` 失败 → 才进入 decode → **seq1 产出第二个 token**

```
seq1 的 token 时刻:  step 5 ─────────────────────────────── step 41
                     token#1          ITL ≈ 36 步 × 57 ms ≈ 2052 ms        token#2
```

实测 ITL max = 1984 ms ✓（第 5 步与第 41 步之间 36 步，均值 ~55 ms）

**所以：**

> 相位分离不是在"先后两个大块"里制造空洞，而是在**每一个提前 admit 完的 seq 的等待期**里制造空洞。
> 因为 admit 串行，**总有人已经 prefill 完、在等 decode，而系统正在给别人做 prefill。**

对比 short 场景（budget 1024，prompt 均 ~600，一步装完一条）：

| 步号 | 1 | 2 | … | 8 | 9 | 10 | … |
| :--- | ---: | ---: | :--- | ---: | ---: | ---: | :--- |
| prefill tok | 606 | 597 | … | 627 | 0 | 0 | … |
| decode tok | 0 | 0 | … | 0 | **8** | **8** | … |
| 步耗时 | 31.1 | 28.0 | … | 38.3 | **9.3** | **8.8** | … |

seq1 在步 1 得 token#1，要等到步 9 才得 token#2 → ITL ≈ 8 × 31.8 ≈ 254 ms（实测 max 231 ms ✓）。
之后每有 1 条 seq 完成、腾出块 admit 一条新的，就再插 1 步 prefill（~32 ms）。

**这个前提何时才成立？**

已经有人指出过：**旧 base 场景（budget = 16384）测不出收益**——那时 budget ≥ 一批 seq 的总 token 数，一步就能把整批 admit 完并 prefill 完，此后全程 decode，**相位分离的代价消失**。

所以决定相位分离代价的是两个量的比值：

```
代价 ∝ (一批 admit 所需的 prefill 步数) × (每步时长) × (等待中的 decode seq 数)
       ↑ budget 越小，这个越大；budget ≥ 一批总量时归零
```

**结论**：不是"相位分离影响 TPOT"或"不影响 TPOT"，而是 ——
**当 budget 小于"一批请求的总 token 数"时，prefill 被迫串行展开，相位边界就落进了别人的 decode 里。**
budget 越小、prompt 越长，落进去的边界越多、每条边界越贵。

### 2.5 为什么 main 要这样设计：CUDA graph 的约束

不是实现偷懒。main 的 decode 走 **CUDA graph replay**（固定 batch、静态 buffer），而 prefill 需要变长执行 + `cu_seqlens`，只能走 **eager**。两者元数据形态不同，**混在同一步就上不了 graph**。

所以 main 只能整步二选一。V1 的解法是"同一步内既跑 decode 又跑 prefill"，代价是**混合批里的 decode 也被迫走 eager**——这正是 C0 里那个"7,854 个 decode token（占 decode 5.88%）走 eager"的来源。

> **一句话总结：V1 用「放弃 5.88% decode token 的 graph 加速」换来了「prefill 期间 decode 不停摆」。** 前者是均摊的小额税，后者是偶发的大额卡顿——这笔交易在长 prompt 下划算，在短 prompt 下不划算（正是 B4 三场景的结论）。

### 2.6 代价为什么记在 ITL、而不是 TTFT

一个自然的反驳（2026-10-14 追问）：

> 「这段等待是用来做 prefill 的，那它不该记在 **TTFT** 里吗？」

**一半对。** 同一段 GPU 时间，站在不同 seq 上看，归属的指标不同：

| 步 6~40 这段 GPU 时间 | 对 seq1 | 对 seq8 |
| :--- | :--- | :--- |
| 该 seq 首 token 是否已产出 | ✅ 步 5 已产出 | ❌ 步 40 才产出 |
| 这段时间落入哪个窗口 | **ITL**（token#1 → token#2） | **TTFT**（排队等前 7 条 prefill） |
| 记作 | ITL 空洞 ≈ 2.0 s | TTFT 排队 ≈ 2.0 s |

**关键：TTFT 的窗口在首 token 处就关闭了。** seq1 在步 5 已经"开口说话"，此后系统去做别人的 prefill——这段只能记进它的 ITL。

**实测印证**（`b4_ttft_vs_itl.py`，三场景 r1，比值 = main ÷ V1）

| 场景 | TTFT p50 | TTFT p99 | TTFT max | ITL p50 | ITL p99 | **ITL max** |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 短 prompt | 1.04× | 1.04× | 1.03× | 1.00× | 1.19× | **5.04×** |
| 长 prompt | 1.00× | 1.00× | 1.00× | 0.99× | 3.32× | **20.35×** |
| 混合 | 1.03× | 1.02× | 1.02× | 1.00× | 3.79× | **14.32×** |

**TTFT 两版逐位相同 → 相位分离在 TTFT 上没留下任何痕迹。**

原因是：两版的**总 prefill 工作量与串行排布方式相同**（V1 每步也只吃一个 chunk），所以第 k 条 seq 的 TTFT 由"前 k−1 条的总 prefill 量"决定——两版一样。V1 改变的不是 prefill 排布，而是"**已出 token 的 seq 能否在 prefill 步里插进去**"。

**由此得到两个指标的瓶颈分工：**

| 指标 | 瓶颈 | chunked prefill 能否改善 |
| :--- | :--- | :--- |
| **TTFT** | prefill **吞吐**（排队深度 × 单条 prefill 时长） | ❌ 几乎不动 |
| **ITL / TPOT 尾部** | prefill 与 decode 的**交织方式** | ✅ 这才是它动的地方 |

> **若只盯 TTFT，会完全看不到这个优化的价值。** 它不加快任何一条 seq"开始说话"的时间，只保证已开口的 seq 不哑掉。
>
> 一句话：**TTFT 度量"你多久开始说话"，ITL 度量"你说话是否连贯"。** main 让 seq1 在步 5 开始说话，然后哑了 2 秒——这 2 秒只能记在 ITL 上。

## 三、实测分解：两版抢占都是 0

| 场景 | 分支 | 纯 prefill 步 | 混合步 | **nd==0 停顿步** | 停顿段数 | **最长连续停顿** | 停顿占墙钟 | ITL p50 | ITL max | 抢占 |
| :--- | :--- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| short | V1 | 1 | 92 | **1** | 1 | 1 | 0.2% | 9.0 ms | 46 ms | **0** |
| short | main | 96 | 0 | **96** | 88 | 8 | 14.6% | 9.0 ms | 231 ms | **0** |
| long | V1 | 5 | 467 | **5** | 1 | 5 | 0.4% | 25.1 ms | 98 ms | **0** |
| long | main | 480 | 0 | **480** | 88 | **40** | **35.6%** | 24.8 ms | **1984 ms** | **0** |
| mix | V1 | 1 | 281 | **1** | 1 | 1 | 0.1% | 17.9 ms | 85 ms | **0** |
| mix | main | 288 | 0 | **288** | 66 | 24 | 28.5% | 17.9 ms | **1219 ms** | **0** |

### 三处自洽的交叉验证

1. **停顿步数对得上工作量**：main 的 480 个停顿步 = 96 条 × 5 chunk（长 prompt ≈ 4700 token ÷ budget 1024）。所以 main **也做了 chunk 切分**——它的问题不是"没切"，而是"切了之后整步只做 prefill"。
2. **最长连续停顿对得上 ITL max**：long 场景 40 步 × 55.8 ms ≈ 2.23 s ≈ ITL max 1984 ms。
3. **抢占列全为 0**：排除了第 3 类来源，把抖动干净地归因到第 1 类。

### 最关键的一行

**三场景的 ITL p50 两版逐位相同**（9.0/9.0、25.1/24.8、17.9/17.9），差异全在尾部：

> **V1 没有让出字变快，它只让"卡顿"消失。** 这正是流式体验的核心——用户感知的是那一次 2 秒的静止，不是均值。

## 四、离线实验的效度边界

### 测得出（机制层）
- ✅ **相位分离的消除**——这是本实验真正验证的东西，且验证得很干净（停顿步 480 → 5）。
- ✅ **抢占的代价**——A4 组已经单独量化过（整段重算 768~1025 token）。
- ✅ **混合步的成本**——V1 的残余抖动（long 场景 ITL max 98 ms vs main 纯 decode 步 ~25 ms）。

### 测不出（到达层）
- ❌ **新请求到达造成的抖动**。离线一次性提交所有请求，没有"运行中到达"这个扰动源。

我们用「N=96 ≫ 并发 7~8」的**初始积压**来替代到达过程。这个替代的相似与差异：

| | 相似 | 差异 |
| :--- | :--- | :--- |
| 状态量 | 都造成 waiting 长期非空 → prefill 与 decode 竞争 | — |
| 时间形态 | — | 在线到达是**持续、随机**的外部扰动；离线积压是**一次性形成**的初始状态，抖动集中在 admit 波次 |
| 对 ITL 尾部 | — | 在线的抖动**分布更均匀**、更难被"峰值并发"这类静态参数刻画 |

**结论：离线实验对「流式平滑性」是必要不充分的。**
- 必要：它证明了 chunked 机制**能**消除 prefill→decode 的停顿。
- 不充分：它无法回答"在真实到达率下，TPOT 尾部会被压到什么程度"。

### 一个容易踩的反直觉点

**如果负载改成 N ≤ 并发上限（所有请求同时 admit、池够、无抢占），两版会完全相同——那时确实只剩抢占能造出抖动。**
但那种配置下 waiting 恒为空，第 1 类抖动源不存在，**实验也就测不到任何东西了**。本实验必须保留积压（N ≫ 并发）才有信号——而积压一旦存在，第 1 类就必然发生。

---

## 五、若要补齐「到达层」

按投入从低到高：

1. **中途注入**（最小改动）：先提交一批，等它们进入稳态 decode 后，再注入一批长 prompt。观察注入瞬间的 ITL 尖峰。这能模拟"到达"的**单次冲击**，代价是十几行改动。
2. **泊松到达仿真**：按 `λ` 持续提交，跑固定时长。可以得到真实意义上的 TPOT p99 随 `λ` 的曲线——这才是能对外比较的"流式平滑性"指标。
3. **对照公开数据**：对方是 256 并发 + chunk 1024 的在线口径，我们是离线受控口径，**指标定义本身就不可直接比**（见 B5 的「同一策略在不同基线上收益落在不同指标上」）。

> 建议：把 1 作为 B 组的补充场景（成本低、直接回答"到达冲击"），2 留给需要对外给数的场合。
