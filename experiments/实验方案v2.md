# 实验方案 v2：正确性 / 目的达成 / 瓶颈定位

对象：V1（running 优先混合调度 + chunked prefill）vs main（waiting 优先、prefill/decode 相位分离）。

| 组 | 回答的问题 | 主判据 | 前置条件 |
| :--- | :--- | :--- | :--- |
| **A 正确性** | 新路径是否算错 | 数值层等价：同一位置 logits 差异 ≤ bf16 精度（实测见 `A_正确性结论.md`） | — |
| **B 目的达成** | ITL 是否变平滑、TTFT 代价是否可接受、利用率是否上升 | ITL 尾部与 CV 显著低于 main | A 通过；抢占 = 0 |
| **C 瓶颈定位** | B 的数字由什么机制产生 | C2：`t_mix < t_p + t_d` | A 通过；抢占 = 0 |

A 不通过 → 先修 bug，B/C 结论无效。

## 1. 公共约定

### 1.1 硬约束（本机实测：RTX 4060 8G）

| 项 | 值 | 说明 |
| :--- | :--- | :--- |
| 权重 | 1.5 GB（0.6B bf16） | 模型加载的基础显存占用 |
| 单 token KV | 112 KiB（每 block 28 MiB） | 28 层 × 8 kv_heads × 128 dim × 2 B × 2（K/V） |
| KV 池（util=0.90，主方案） | 163 blocks = 41728 tokens | 决定 并发 × 序列长度 的实际上限 |
| KV 池（util=0.95，备选） | 177 blocks = 45312 tokens | 压榨显存可提高上限，OOM 风险增加 |
| block_size | 256 | 每条序列平均浪费半个 block |
| 默认配置 | budget=16384，max_num_seqs=512 | |
| max_model_len | 4096 ~ 32768 均不缩池 | 池只由显存反推（公式与它无关）；放开上限只是长序列多占 block（`max_position_embeddings`=40960，非约束） |

### 1.2 对照组

两版 = git 分支 main 与 V1，除调度外无其他差异。

- **main（基线）**：waiting 优先。有 prefill 就整步做 prefill，resident 的 decode 停摆。
- **V1**：running 优先。每步先推进 decode，再用剩余预算收 waiting / 做 chunked prefill。

### 1.3 确定性采样（A 组前提，两版共用）

现状（`layers/sampler.py`）：Gumbel-max（`argmax(probs / Exp(1))`，`probs = softmax(logits/T)`）+ **全局 RNG**，每步消耗 batch×vocab 个随机数。

- 后果：batch 组成不同（两版、不同 budget）→ RNG 流错位 → 输出不可复现。逐 token 对比时，"不一致"将无法区分 bug 与采样噪声。
- 极小 temperature 不能替代：softmax 内部减 max（实测 T=1e-4 不产生 nan），但并列 logits 由噪声随机决定，仍依赖 RNG 流。
- **方案：实验期替换 `Sampler.forward` 为 argmax**（只 patch 该方法，不改仓库源码，两版共用；B/C 一并启用以保全程可复现）。不要用 `TORCHDYNAMO_DISABLE=1`——会连带关闭 layernorm / RoPE / activation 的 compile。

### 1.4 计时口径

- per-step：`perf_counter` + `torch.cuda.synchronize()`。
- TTFT / ITL 一律 per-request（混批下 batch 级时间不可分解）。
- 每轮先 warmup（图捕获、编译在 init / warmup 内完成），首步不计入。
- 单进程独占 GPU，无其他 CUDA 活动。

### 1.5 抢占监控（全程必录）

记录 `can_allocate` / `can_append` 失败次数与 `preempt()` 调用次数。

抢占把 seq 打回 waiting 并重算 prompt，凭空制造 prefill 工作，污染 A/B/C 全部观测。**B/C 要求抢占 = 0，否则调低并发重跑。**

## 2. 实验 A：正确性

目的：验证 V1 新增的 4 条路径没有算错。

| # | 新路径 | 出错后果 |
| :--- | :--- | :--- |
| P1 | 混合批里的 decode seq 走 `prepare_prefill` 通用分支 | slot_mapping / positions / cu_seqlens 算错 → 静默写脏 KV |
| P2 | `need_logits` 掩码（mid-chunk 不算 lm_head） | token 与 seq 错位 |
| P3 | `is_uniform` 切执行路径（纯 decode 走 graph，其余 eager） | graph replay 的 context 填充错位 |
| P4 | 抢占重入（`num_cached_tokens` 与真实 KV 是否一致） | 读脏 KV / 丢 token |

### A1 分块不变性

**⚠️ 2026-10-12 实测修正：判据已改。** 原定「逐 token 完全一致」**不成立，且 main 基线自身也不满足**。

原因：① 分块改变 attention 浮点归约顺序；② 不同 budget 改变 batch 组成 → varlen 打包布局变化（**即使某条 seq 自身没被分块**——实测 seq1 长度 512、在 budget=512 下整条处理，仍发生翻转）；③ 单点翻转经自回归放大成整条序列不同。

**修正判据：数值层等价** —— 比较同一输入位置上的 logits（top-5 索引一致 + max(Δlogit) 落在 bf16 精度内）。

- 自变量：budget ∈ {256, 512, 2048, 16384}
- 负载：N=12；长度 {256,512,640,768,1024,1500,2048,2560,3072,3200,4096,512}；O=64（ignore_eos）
- **实测**：分块 vs 不分块 Δ = 0.0625 ~ 0.125，相对 absmax 3.2e-3 ~ 6.5e-3 —— 正好是 bf16 相对精度 2⁻⁸ ≈ 3.9e-3 的量级；top-5 索引 5/5 一致、首 token 相同
- 详见 `A_正确性结论.md`

### A2 跨实现等价

main vs V1，单条 seq、固定 prompt，比较「处理完 prompt 那一次采样」的 logits。

- 判据：**同一位置 logits 逐位相同**（max(Δlogit) = 0）
- **实测：budget ∈ {16384, 2048, 512} 全部 Δ = 0.000000，top-5 索引 5/5 一致，首 token 相同（25177）** → V1 的 P1/P2/P3 在数值上零副作用
- 对齐坑：main 无 `need_logits` 掩码，mid-chunk 也会采样一次再丢弃 → probe 序列更长，须按 `probe[len - max_tokens]` 取；直接取 `probe[0]` 会拿到 prompt 中间位置的 logits（踩过）

### A3 数值对齐（graph vs eager）

- **实测结论：已合并进 A2。** `enforce_eager` 与默认（graph）结果**逐字相同**，graph 不引入任何差异 → P3 排除。
- 附带：比较 logits 时 max(Δlogit) 的实测量级为 bf16 舍入（相对 3e-3），可作 A1 的容差依据。

### A4 抢占重入

**⚠️ 2026-10-12 实测完成，判据已按实测重写。** 详见 `A4_抢占重入结论.md`。

唯一自变量 = **KV 池块数**（`--force-delta`），prompt / 注入方式 / budget 全同 → **prefill 批组成一致**，差异只出现在 decode。对照不能"逐条串行跑"（批组成全盘不同，噪声盖过信号）。

- 负载：N=24，plen=768，O∈[240,792]；强制池 72（= admit 所需），需求 132 块 → 必然抢占
- 判据：
  1. L1 全部完成 / 长度正确 / 输出非空，实验组抢占 > 0 且对照组 = 0
  2. L1' 结构不变式：`len(block_table)*256 >= num_tokens` 且 `num_cached_tokens <= len(block_table)*256`
  3. L2 数值层：按 **token id 求交**比较 logits，Δ 量与**实测噪声地板**同量级
  4. **L3（核心）**：被抢占 seq 的首异位置**不得 == 抢占点**
- **实测：全部 PASS**。8 条被抢占 seq 中 6 条可评价，0 条首异位置落在抢占点（5 条晚于、1 条完全一致）
- 附带发现：9 次抢占里 **7 次重入 `num_cached_blocks = 0` → 整段重算 768~1025 token**，覆盖的是比"前缀命中续算"更危险的路径

**判据为什么必须这么定**（三个坑）：

1. 按 **rank** 对齐比 top-5 值 → top-5 集合错位时放大成 25% 假差异；必须按 **token id 求交**再比数值
2. 缩小池必须保证 `强制池 >= admit 所需`，否则 admit 组成变化 → **prefill 批组成也变** → 抢占前就分歧
3. **跨运行比较不存在"Δ 落在 bf16 精度内"**：实测噪声地板 max 相对 Δ = 3.2e-2 ~ 5.9e-2，是 bf16 表示精度（3.9e-3）的 8~15 倍。判据只能是"与实测地板同量级"
4. `torch.argmax` 与 `topk` 平局时 tie-break 不一致（12384 点中 50 点）→ "top-1 索引"不是干净指标

### A5 通过标准（2026-10-12 实测）

| 判据 | 标准 | 实测 |
| :--- | :--- | :--- |
| A2 | 同一位置 logits Δ = 0 | **PASS**（3 档 budget 全 0.000000） |
| A1 | top-5 索引一致 + Δ 与噪声地板同量级 | **PASS**（相对 3e-3 ~ 6e-3，同批组成） |
| A3 | —— | 合并进 A2（eager 与默认逐字相同） |
| A4 | 全部完成 + 首异位置不落在抢占点 + Δ 与地板同量级 | **PASS**（V1 0/8、main 0/9；Δ 0.90~1.24× 地板） |

**A4 噪声地板实测**（同配置重跑：token 完全一致、logits Δ = 0.000000；仅解码批行数不同：max Δ = 3.2e-2 ~ 5.9e-2）。

逐 token 严格一致**不作判据**（main 基线自身也不满足，见 A1）。

**附带产出**：P2（need_logits）收益被量化 —— main 白算 lm_head 的次数 = chunk 数 − 1（prompt=3200：budget=2048 白算 1 次、budget=512 白算 6 次，与采样调用次数完全吻合）。

## 3. 实验 B：目的达成

### B1 为什么默认 bench 负载测不出

默认负载：256 条、P∈[100,1024]、O∈[100,1024]。

1. 需求 256×1124 ≈ 288k tokens ≫ 池 41728 → 必然高频抢占 → 混合步大多来自抢占重算，不是调度策略；
2. prompt 太短 → 单次 prefill 仅几十 ms → main 的 decode 停摆轻微。

### B2 负载设计：制造「waiting 长期非空 + resident 满载」稳态

关键：等待中的 seq 不占 KV。注入数远超 resident 上限，waiting 就长期非空。

| 参数 | 值 | 说明 |
| :--- | :--- | :--- |
| N | 96 | 离线一次性注入 |
| P | 均匀 [2048, 4096] | 长 prompt，prefill 时长可观 |
| O | 均匀 [64, 256] | 完成时间分散 → prefill 事件分散插入 |
| max_model_len | 8192 | 放开（P+O 最大 4352 > 4096；不缩池） |
| budget | 16384 | 默认 |

预期（校核用，不达就调负载）：

| 量 | 预期 | 依据 |
| :--- | :--- | :--- |
| resident | ≈ 12 条 | 163 blocks ÷ 每条约 13 blocks（(3072+160)÷256） |
| 峰值 KV | ≈ 12×13 = 156 / 163 blocks | 余量 7 → 预期不触发抢占（仍以 §1.5 全程监控为准） |
| prefill 步占比（main） | ≈ 7% | 96 / (96 + 96×160/12)；每个 prefill 步 = 一次 decode 停摆 |

S2 加压场景（验证"收益 ∝ prefill/decode 比"）：

- O 缩到 [32, 96]：decode 步 ≈ 0.4×，prefill 步占比升到 ≈ 1/6；
- 或 budget 降到 2048：chunked 真正生效，同时放大 TTFT 代价。

### B3 指标与判据

| 目的 | 主指标 | 预期 |
| :--- | :--- | :--- |
| 1 ITL 平滑 | ITL p50/p90/p99/max、CV = std/mean、双峰性 | V1 的 CV 与 p99/p50 显著低于 main |
| 1' 空洞 | 空洞计数：ITL > 3×p50 的次数 | V1 → 0，或远少于 main |
| 2 TTFT 不牺牲 | TTFT p50/p99 | V1 相对 main 增幅 < 阈值（基线测出后定，初值 10%） |
| 3 利用率 | 混合步占比、每步平均 token 数、预算填充率 | V1 混合步 > 0（main 恒 0）；每步 token 数更高 |
| 旁证 | 端到端吞吐 | V1 ≥ main（不作主判据） |

### B4 陷阱

1. 抢占必须为 0（§1.5）：重算的 prefill 混入"混合步" → 指标失效，调低并发重跑。
2. 别只报 p50：平滑是分布性质；两版均值可能几乎相同，差异全在尾部。
3. 同一负载必须喂给两版：同 prompt 集合、同 seed 的 sampling params。
4. 观测窗口要够长：空洞占比 7% 时，p99 至少需要几百个 interval 才有意义。

## 4. 实验 C：瓶颈定位

目标：解释 B 的数字从哪来。按重要性排序：

### C2 混合批的物理基础（核心）

- H1：`t_mix(P+D) < t_p(P) + t_d(D)`
- H2：`t_mix(P+D) ≈ max(t_p, t_d)`（decode 接近"白送"）
- 方法：固定 P（prefill token 数）、D（decode 条数）组合，分别构造"只 P"、"只 D"、"P+D"三种 batch，测 forward 时间
- 用途：B 组"利用率提升"的因果证据；H1 不成立则整个改动的收益解释不成立

### C1 步级时间分解

埋点 `schedule()` / `prepare_*()` / `run_model()` / `postprocess()`，按步类型分组（纯 P / 纯 D-graph / 纯 D-eager / 混合）。回答：CPU 调度开销占比多大（0.6B + 小 batch，CPU-bound 是常见嫌疑）。

### C3 CUDA graph 收益量化

纯 decode 批，`enforce_eager` True / False 对比每步时间。量化 P3 的代价：混合步被迫走 eager，损失多少。

### C4 need_logits 收益量化

强分块场景，开 / 关掩码对比。lm_head 代价：vocab 151936 × hidden 1024 → mid-chunk 的每个 token 都是浪费。量化 P2 的独立收益。

### C5 profiler 归因

`torch.profiler` 抓 3-5 个代表性 step，看 timeline 与 top kernels。判断 GPU-bound / CPU-bound，以及 attention / lm_head / elementwise 的占比。

### C6 参数敏感性（附属）

budget × 并发 的二维扫描。产出甜点区，回答"默认 16384 是否合适"。（budget 不作 B 的自变量：它同时改变分块粒度与 decode 容量，解释力打折。）
