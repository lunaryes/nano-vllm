# C2：混合批的物理基础 —— 加法性成立，但窗口很窄

对象：V1（running 优先混合调度）vs main。实验日 2026-10-12，分支 V1。
数据：`results/c2_V1b.json`、`results/c2_mainb.json`、`results/c2_shape_D{8,32}.json`；分析输出 `results/c2_analyze_V1b.txt`。

## 0. 结论速览

**H1（`t_mix < t_p + t_d`）成立，但只在 D ≤ 16 成立；D ≥ 32 反转。**

| 量 | 实测 |
| :--- | :--- |
| 混合批的收益来源 | **权重读取 / kernel 固定开销的分摊**，不是"更多算力" |
| 收益窗口 | D ≤ 16（`mix/sum` 0.54 ~ 1.00） |
| 失效临界 | **D ≈ 32**，与 P 无关（`mix/sum` 1.11 ~ 1.25） |
| D=64 时的代价 | 混合步比"分开两步"**慢 20~38%**（`a_est` = −27 ~ −53 ms） |
| 单条 decode 的相对成本 | P 越大越便宜：P=512 时 +15%，P=4096 时 **+6%** |
| **失效的根因** | 混合批里 decode 必须用 `flash_attn_varlen_func` + `block_table` 读 **paged KV**，比纯 decode 的专用 kernel (`flash_attn_with_kvcache`) 慢得多（C2b 定位） |

**对 B 组的直接含义**：V1 的混合调度只有在 **resident ≲ 16** 时才有正收益。B2 设计的 resident ≈ 12 落在窗口内，但余量很小 —— 一旦并发上去，混合步会从"白送 decode"变成"拖累 prefill"。

**两版完全一致**（P=4096,D=8：V1 242.9ms / main 244.3ms）。C2 是**执行层属性**，与调度策略无关 —— 这一点很重要：收益来自 batch 组合本身，V1 只是"把这个组合实际调度出来"。

## 1. 问题与方法

### 1.1 H1 / H2 的物理含义

V1 每步先把 resident 的 decode 推进一格，再用剩余预算收 prefill。相对于 main 的"有 prefill 就整步不做 decode"，V1 把两次 forward 合并成一次。

- **H1**：`t_mix(P+D) < t_p(P) + t_d(D)` —— 合并比分开省时间
- **H2**：`t_mix(P+D) ≈ max(t_p, t_d)` —— decode 部分接近"白送"

若时间模型为 `t(n) = a + b·n`（a = 每步固定开销，b = 每 token 边际），则

```
t_mix = a + b(P+D) = t_p + t_d − a
⇒ mix_over_sum = 1 − a/(t_p+t_d)
⇒ 固定开销估计  a_est = t_p + t_d − t_mix
```

所以 H1 成立 ⇔ `a_est > 0`；H2 成立 ⇔ `a_est ≈ min(t_p, t_d)`。

### 1.2 为什么绕过调度器

直接跑 `llm.generate` 无法控制 P 和 D：调度器决定每步收多少 prefill、resident 有多少。所以本实验在 **ModelRunner 层手工构造 batch**，调 `runner.run(seqs, flag)`，用 CUDA event 计时。

可行性来自两条源码事实：
- `run()` **不修改 seq 状态**（只读 `num_cached_tokens` / `num_scheduled_tokens` / `block_table`）→ 可重复计时
- 混合批走 `is_uniform=False` → `prepare_prefill`，其中 decode 态 seq（`num_cached = len−1`、`scheduled = 1`）走通用分支 —— 正是 A 组 P1 路径

### 1.3 三种 batch

| 名称 | 构造 | 语义 |
| :--- | :--- | :--- |
| P-only | 1 条 seq，`num_cached=0`，`scheduled=P` | 纯 prefill 步（main 的一步） |
| D-only | D 条 seq，各 `num_cached=Ld−1`，`scheduled=1` | 纯 decode 步（main 的另一步） |
| mix | 上面两者拼一个 batch | V1 的混合步 |
| d_gen | D 条 decode seq，走 **prefill 路径** | 分离"路径差异"与"token 组成差异" |

固定 `Ld = 2048`，块表不重叠（prefill 用 `[0, nb_p)`，decode 共享 `[nb_p, nb_p+nb_d)`），池 163 blocks 远未用满。

### 1.4 为什么统一 `enforce_eager=True`

默认配置下纯 decode 步走 CUDA graph，而混合步（`is_uniform=False`）被迫走 eager。直接比较会混入 graph 的加速，无法归因。三条路径统一 eager 后，差异只来自 batch 组成。graph 的收益留给 C3 单独量化。

代价：本实验测的是 **eager 下的物理特性**，绝对值会高于默认配置，但**比值（mix/sum）不受影响**。

## 2. 结果

### 2.1 绝对时间（gpu_ms_min，`enforce_eager=True`，Ld=2048）

**t_p（纯 prefill）** —— 随 P 超线性增长（attention O(L²) + MLP 由 memory-bound 转 compute-bound）

| P | 512 | 1024 | 2048 | 4096 |
| :--- | ---: | ---: | ---: | ---: |
| t_p 中位数 | 28.8 | 42.0 | 94.1 | 224.0 |

**t_d（纯 decode）** —— 在 D ≤ 16 完全平坦

| D | 1 | 4 | 8 | 16 | 32 | 64 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| t_d (P=2048) | 22.1 | 24.9 | 25.3 | 25.8 | 25.9 | 44.9 |

**D 从 1 涨到 32（32 倍），decode 步只慢 17%** —— 这是 H1 能成立的根本原因：纯 decode 批已被固定开销支配。

**t_mix（混合）** —— 随 D 明显增长

| D | 1 | 4 | 8 | 16 | 32 | 64 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| P=512 | 32.5 | 32.0 | 33.7 | 43.4 | 61.6 | 100.1 |
| P=1024 | 48.3 | 51.9 | 57.3 | 65.9 | 84.6 | 122.2 |
| P=2048 | 101.6 | 104.4 | 109.6 | 119.1 | 139.5 | 180.5 |
| P=4096 | 238.7 | 239.6 | 242.9 | 254.8 | 277.9 | 320.2 |

### 2.2 H1 / H2 判定

**`mix_over_sum = t_mix/(t_p+t_d)`**（<1 = 混批有收益）

| P＼D | 1 | 4 | 8 | 16 | 32 | 64 |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 512 | 0.577 | 0.544 | 0.622 | 0.798 | **1.123** | **1.380** |
| 1024 | 0.728 | 0.776 | 0.865 | 1.001 | **1.254** | **1.402** |
| 2048 | 0.881 | 0.873 | 0.933 | 0.993 | **1.164** | **1.295** |
| 4096 | 0.965 | 0.957 | 0.966 | **1.039** | **1.116** | **1.201** |

- **H1(robust) 成立 15/24 = 62%**
- **失效临界一律在 D = 32**（P=4096 提前到 16）
- P 越大，`mix/sum` 越接近 1（收益绝对量变小，但从不亏太多）

**`mix_over_max = t_mix/max(t_p,t_d)`**（→1 = decode 被吸收）

| P＼D | 1 | 4 | 8 | 16 | 32 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 2048 | 1.090 | 1.102 | 1.189 | 1.265 | 1.485 |
| 4096 | 1.061 | 1.061 | 1.068 | 1.153 | 1.245 |

**`mix/p = t_mix/t_p`**（混合步相对纯 prefill 步的膨胀）—— **P 越大越"白送"**

| P＼D | 1 | 8 | 16 |
| :--- | ---: | ---: | ---: |
| 512 | 1.150 | 1.151 | 1.479 |
| 1024 | 1.121 | 1.358 | 1.578 |
| 2048 | 1.090 | 1.189 | 1.265 |
| 4096 | **1.061** | **1.068** | 1.153 |

P=4096 时，加 8 条 decode 只让 prefill 步慢 **6.8%** —— H2 的"白送"在这个区间成立。

### 2.3 固定开销与边际成本

**`a_est = t_p + t_d − t_mix`（ms）** —— 正值 = 混批省下的固定开销

| P＼D | 1 | 8 | 16 | 32 | 64 |
| :--- | ---: | ---: | ---: | ---: | ---: |
| 512 | 23.80 | 20.44 | 10.99 | **−6.75** | **−27.57** |
| 1024 | 18.09 | 8.90 | −0.05 | **−17.15** | **−35.01** |
| 2048 | 13.74 | 7.86 | 0.88 | **−19.70** | **−41.12** |
| 4096 | 8.70 | 8.62 | −9.48 | **−28.87** | **−53.62** |

D ≥ 32 时 `a_est` 变负 —— 混合批不但没省下固定开销，还**额外多付**了 17~54 ms。

**对 D 的边际成本**（线性拟合 D∈[1,32]，避开 D=64 台阶）

| P | 纯 decode 批 | 混合批（净增量） | 比值 |
| :--- | ---: | ---: | ---: |
| 1024 | 0.083 | 1.164 | **14.1×** |
| 2048 | 0.085 | 1.233 | **14.5×** |
| 4096 | 0.081 | 1.317 | **16.3×** |

> ⚠️ **这个 14~16× 的比值有误导性**：分母（纯 decode 的边际）接近 0，比值被放大。含义更稳的口径是**总量比**：D=32 时混合批里 decode 花掉 `t_mix − t_p = 45.4ms`，而同样 32 条单独跑只要 26.4ms → **1.7 倍**。两个口径都对，但要说清楚分母是什么。

## 3. 机制定位（C2b）

"混批内 decode 变贵"有两个候选机制，用两个独立旋钮分离（`results/c2_shape_D*.json`）。

### 3.1 旋钮设计

| 旋钮 | 操作 | 改变的变量 | 保持不变的 |
| :--- | :--- | :--- | :--- |
| 1 拆 P | 把 P 拆成 k 条长度 P/k 的 prefill | `max_seqlen_q`: 2048→128 | 总 token 数、模型路径 |
| 2 去历史 | decode seq 的长度从 2048 改成 1 | **是否触发 `block_tables` 路径**（`cu_seqlens_k > cu_seqlens_q`） | 总 token 数、seq 数、seq 状态类型 |

旋钮 2 是关键：历史长度为 1 时 `cu_seqlens_k == cu_seqlens_q`，`prepare_prefill` 不准备 `block_tables`，attention 用**刚算出的本地 k,v** 而非从 `k_cache` 按块表 gather。

### 3.2 结果

| 配置 | t_mix（有历史） | t_mix（无历史） | t_p（同形状） | t_d |
| :--- | ---: | ---: | ---: | ---: |
| P=2048, D=8 | 107.5 | **95.2**（−11%） | 91.8 | 23.2 |
| P=2048, D=32 | 141.7 | **97.3**（−31%） | 93.9 | 26.4 |

拆 P（旋钮 1）：`t_mix` 从 107.5→90.2（−16%），但 **`t_p` 同步从 91.8→76.9（−16%）**，`mix/sum` 几乎不变（0.935→0.899）→ **`max_seqlen_q` 不是额外成本的来源**，它只影响 prefill 自身。

### 3.3 结论

**去掉 decode 的历史后，往混合批里塞 32 条 decode 只要 `97.3 − 93.9 = 3.4 ms`（几乎白送）。**

所以：

```
混合批里 32 条 decode 的总成本  = t_mix − t_p      = 47.8 ms
其中 linear 层（32 token）      ≈ 3.4 ms      （由无历史对照隔离）
其中 attention（读 2048 KV）     ≈ 44.4 ms     ← 全部额外成本在这里
同样 32 条走专用 decode 路径     = t_d            = 26.4 ms
```

**根因：混合批被迫用 `flash_attn_varlen_func(q, k_cache, v_cache, block_table=…)` 来读 paged KV；而纯 decode 用 `flash_attn_with_kvcache`。前者是 prefill 的 varlen 接口硬套 block_table，读 paged KV 的效率明显低于专用 decode kernel。**

这解释了为什么：
- 小 D 时 `t_p` 自身很大，"多花几 ms 读 KV"被淹没 → H1/H2 成立
- 大 D 时 KV 读取量 ∝ D × Ld 线性增长，且效率又低 → 反超 `t_d`

也解释了 `t_d` 在 D=64 的台阶（27→45ms）：那是专用 kernel 本身从"固定开销支配"转到"KV 带宽支配"的拐点，与混合批无关。

## 4. 对 B 组的含义

### 4.1 收益窗口

| resident（≈ D） | 预期 |
| :--- | :--- |
| ≤ 8 | 明确收益，`mix/sum` 0.87~0.97 |
| 16 | 临界，`mix/sum` ≈ 1.0 |
| ≥ 32 | **负收益**，`mix/sum` ≥ 1.11 |

**B2 设计的 resident ≈ 12 落在窗口内**（对应 D=8~16，`mix/sum` 0.93~0.99），但余量很小 —— 实际 resident 由 KV 池决定，若负载偏长导致 resident 掉到 8 以下反而更有利，升到 20+ 就会侵蚀收益。

### 4.2 一条必须写进 B 组结论的约束

**"混合调度提升利用率"这个说法有适用边界**，不能无条件陈述：

- 成立的机制是**固定开销分摊**（权重只读一次、少一次 kernel launch）
- 失效的机制是**读 paged KV 的接口效率**（varlen vs 专用 decode kernel）
- 两者的相对大小由 `D × Ld`（KV 读取量）对 `P`（prefill 固定开销）决定

所以正确的表述是：**在 resident 数适中、prefill 占主导时，混合调度接近"decode 白送"；resident 过大时它反而拖慢整步。**

## 5. 局限

1. **`Ld` 固定 2048** —— KV 读取量 ∝ D × Ld。Ld 更小则失效点更靠后。这是下一个该扫的维度。
2. **P 是单条 seq** —— 真实调度里 prefill 可能由多条 prompt 拼成。C2b 的旋钮 1（拆 P）显示拆开只降低 `t_p` 本身，不改变 `mix/sum`，所以推测影响有限，但未直接验证。
3. **统一 eager** —— 绝对值高于默认（graph）配置；比值不受影响，但"C3 graph 收益"与"混合批被迫 eager 的代价"要合起来看。
4. **桌面 GPU** —— 非独占环境，t_p 单次抖动可达 4%（P=512 时更高），已用 `min` + 跨 D 中位数降噪。
5. **未做 profiler** —— 3.3 节的根因是"两个旋钮 + 排除法"推出的，`flash_attn_varlen_func` 的 paged-KV 低效尚未用 timeline 直接证实，留给 C5。

## 6. 踩过的坑（方法论，必须记）

### 6.1 `run()` 第二参数语义在两版相反 —— 导致一整轮数据作废

| 分支 | 签名 | `True` | `False` |
| :--- | :--- | :--- | :--- |
| V1 | `run(seqs, is_uniform)` | decode | prefill |
| main | `run(seqs, is_prefill)` | **prefill** | **decode** |

第一轮我对两版都传 `False`：V1 正确，**main 的 "P-only" 实际执行的是 `prepare_decode`**（只处理 1 个 token）。症状是 `t_p` 恒定 22ms、与 P（512→4096）完全无关 —— 而 prefill 的 attention 是 O(L²)，不可能平。

修法：用 `inspect.signature(runner.run).parameters[1]` 取参数名自动映射，并加自检 `t_p(4096)/t_p(512) > 1.5`（实测 7.79 / 8.08）。

`main` 的 `prepare_decode` **没有** `num_cached_tokens == len−1` 断言，所以传错不会崩，只会静默给出错误数据。V1 有断言，反而安全。

### 6.2 其它

- **`min` 而非 `median` 作主判据**：CPU 抖动只会让时间变长，`min` 最接近真实 kernel 时间。
- **块表必须不重叠**（prefill 与 decode 分区），否则 `store_kvcache` 互写会污染（对时间影响小，但不利于解释）。
- **decode seq 先真实 prefill 一次填 KV**，避免 attention 读到未初始化显存。
