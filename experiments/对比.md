# vLLM 官方口径对照与混合批 × CUDA Graph：机制、实测、优化路线

> 起因：有人做了同样的优化（混合调度 + chunked prefill），报出 Qwen3-0.6B / 256 并发 / chunk=1024 下：吞吐 +4.6%、P999 步延迟 −36.1%、峰值显存 −3.0%。因此要问：我们的实测与 vLLM 官方在 V1 中引入混合调度 + chunked prefill 后的收益吻合吗？
>
> 数据口径：本文件每一个「我们」的数字，均由 `experiments/vllm_ref_compare.py` 从 `results/*.json` 现算（输出见 `results/vllm_ref_compare.md`），不引用记忆或旧文档转述。
>
> 修正说明：混合批 × CUDA graph 依据 C6/C6b 新测：`c6_prefill_graph.py` / `c6b_bisect.py` → `results/c6_prefill_graph.json`、`figs/c6_prefill_graph.png`。它修正了原 §2 结论。

## 0. 官方收益到底指什么：三条口径必须分开

vLLM 侧的「收益」不是一个数，而是三份性质完全不同的主张：

| #    | 出处                                                                                                  | 主张                                                                                                                                                      | 归因                                                                                                                                                                     |
| :--- | :---------------------------------------------------------------------------------------------------- | :-------------------------------------------------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ①    | [vLLM V1 alpha 博客](https://blog.vllm.ai/2025/01/27/v1-alpha-release.html)（2025-01-27）             | 「up to **1.7x** higher throughput compared to V0」                                                                                                       | 原文：收益来自「comprehensive **CPU overhead reductions** across the entire stack」；并说明 V0/V1 kernels「almost identical」，差异主要来自架构改进（降低 CPU overhead） |
| ②    | [vLLM 官方调优文档 · Chunked Prefill](https://docs.vllm.ai/en/latest/configuration/optimization.html) | (a) 改善 ITL（decode 被优先）；(b) 更好的 GPU 利用率（compute-bound prefill 与 memory-bound decode 同批）                                                 | 调度策略本身                                                                                                                                                             |
| ③    | [SARATHI / Sarathi-Serve, OSDI'24](https://www.usenix.org/conference/osdi24/presentation/agrawal)     | 消除 vLLM 数秒级 generation stall；显著降低 P99 TBT；明确「prioritizing TBT over TTFT」；吞吐「same or better」；尾延迟 SLO 下服务容量 2.6× / 3.7× / 5.6× | 调度策略本身                                                                                                                                                             |

关键结论：

- 只有 ②③ 是关于「混合调度 + chunked prefill」的。
- ① 的 1.7× 是引擎层重建的功劳：多进程 EngineCore、持久化输入、torch.compile、prefix caching、API server 重叠等。
- vLLM 博客讲统一调度器（unified scheduler）那一节，一个性能数字都没有；只讲 `{request_id: num_tokens}` 表示法如何同时支持 chunked prefill / prefix caching / 推测解码。

## 1. vLLM V1 机制：混合批为什么还能吃 CUDA Graph

### 1.1 四个前提

| #    | 机制                                                                                                                           | 作用                                                                                                                   |
| :--- | :----------------------------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| ①    | 统一的扁平批表示：`{request_id: num_tokens}` + 张量化元数据（`query_start_loc` / `seq_lens` / `block_table` / `slot_mapping`） | 批里没有「prefill 分支 / decode 分支」，只有总 token 数 T 这一个自由量。混合批退化成「形状由 T 决定的普通批」          |
| ②    | 按 num_tokens / batch_size 分桶 + padding：`cudagraph_capture_sizes`、`max_cudagraph_capture_size`                             | 实际批填到最近桶，多出来的行用 dummy 掩盖。形状静态化是录图前提                                                        |
| ③    | 在 attention 边界切图（piecewise）：图外 eager 跑 attention，图内跑 attention 之间的一切                                       | attention 之间是 token-wise 的，形状只由 T 决定；attention 形状随每个请求的 seq_len 变。把不稳定的一段摘出去，其余进图 |
| ④    | attention 输出张量作为输入传入（output-as-input）+ `torch._C.Tag.cudagraph_unsafe` + inductor graph partition                  | 让图自己拥有 buffer；N 个 attention 自动切出 N+1 段，不用手写切分                                                      |

官方文档原话：

> 「…we only capture the cudagraph for the piece of graph between attention operations… computation between attentions are usually token-wise and easy to deal with for cudagraph; while the attention operation is non-trivial to be cudagraph compatible. Thus, by running the attention operation in eager mode while the rest operations in cudagraph, we keep the flexibility of the attention operation. … This is why the attention operation in V1 has the output tensor as the input of the attention.」

### 1.2 piecewise 落在一层 Transformer 上

```text
        hidden [T, H]                      T = 本步总 token 数（已 pad 到桶）
   ┌──────────────────────────────────────────────┐
   │  段 i：RMSNorm → QKV GEMM → RoPE       ← CUDA Graph（形状只由 T 决定）
   └──────────────────────────────────────────────┘
                        ↓ q, k, v
   ┌──────────────────────────────────────────────┐
   │  vllm::unified_attention_with_output   ← eager（形状随每个请求的 seq_len 变）
   │  （内部写 paged KV cache + 调 FA3/FlashInfer）
   └──────────────────────────────────────────────┘
                        ↓ o（写进图拥有的静态 buffer）
   ┌──────────────────────────────────────────────┐
   │  段 i+1：O-proj → AllReduce → 残差 → MLP ← CUDA Graph（与下一层前半段合并）
   └──────────────────────────────────────────────┘
```

- 一个 80 层模型：一次 forward 约 81 段图 replay + 80 次 eager attention。
- 绿段内 kernel 间没有 launch 气泡。
- 橙色 attention 形状不固定，只能 CPU 逐次发射，但它是每层最「胖」的 kernel，launch 开销相对可接受。

### 1.3 五档 `CUDAGraphMode`

官方术语：

- **uniform decode batch**：`max_query_len == 1`。
- **non-uniform batch**：prefill 或混合。

| 模式                 | 含义                                                                         | 适用                                                              |
| :------------------- | :--------------------------------------------------------------------------- | :---------------------------------------------------------------- |
| `NONE`               | 关图                                                                         | 调试                                                              |
| `PIECEWISE`          | attention 留图外，其余进图（需要 piecewise 编译）                            | 通用、最灵活                                                      |
| `FULL`               | 对非均匀批（prefill / 混合）也录整图，同 batch_size 的纯 decode 批复用这张图 | 官方注明「good for small models or workloads with small prompts」 |
| `FULL_DECODE_ONLY`   | 只给纯 decode 录整图                                                         | P/D 分离里的 decode 实例                                          |
| `FULL_AND_PIECEWISE` | V1 默认：纯 decode 走整图，prefill / 混合走分段图                            | 官方称通常最快，但最吃显存、捕获最慢                              |

运行时由 **CUDA Graphs dispatcher** 按批组成自动选模式；无合适图时降级 `NONE`。

两条官方边界：

- 只有 FA3 支持对非均匀批做 full cudagraph；FlashInfer / FlashMLA / Mamba 等只支持纯 decode 整图。
- cascade attention 不图安全，用到时一律降级到 `PIECEWISE`。

注意：官方对 chunked prefill 的收益宣传里，「减少 graph 开销」从来不是一条。列表永远是：改善 ITL / 提高 GPU 利用率 / 平滑生成。这与 C6 实测一致。

## 2. 逐维度对照

### 2.1 吞吐：不吻合，而且本来就不该吻合

|                                                | 数值                          |
| :--------------------------------------------- | :---------------------------- |
| vLLM 官方（V1 vs V0，Llama 3.1 8B / ShareGPT） | 最高 1.7×                     |
| 我们 · 官方 bench 口径（stress，提交 256 条）  | 0.990×（V1/main 墙钟 1.011×） |
| 我们 · 受控口径（ctrl，抢占 = 0）              | 0.958×（墙钟 1.044×）         |

不吻合根因：改的层不同。

- 官方 1.7× 的杠杆是 CPU 开销。
- nano-vllm 是单进程离线批处理：没有 OpenAI API server、没有流式解码、没有分词/去分词进程、没有 ZeroMQ IPC、没有推测解码与 LoRA。
- ① 的主要杠杆在本仓几乎不存在。
- 我们的 V1 分支只改了 Scheduler + ModelRunner 的调度路径，等价于 vLLM V1 的「调度器那一半」；① 来自「执行循环那一半」。
- 官方文档自己写：「For optimal throughput, we recommend setting `max_num_batched_tokens` > 8192」——吞吐最优设置恰恰是把 chunk 关掉（或几乎关掉）的区间。
- 官方从没把 chunked prefill 当成吞吐优化来卖。

结论：吞吐这一项「不吻合」是预期内的，不构成矛盾。真正该对照的是 ② 和 ③。

### 2.2 尾延迟（ITL / TBT）：强吻合，逐条吻合

B 组受控三场景，budget = 1024，两版抢占均为 0：

| 场景              | 分支 | ITL CV |  ITL p99 | ITL max | 停顿步 | 最长连续停顿 |
| :---------------- | :--- | -----: | -------: | ------: | -----: | -----------: |
| 短 prompt（768）  | V1   |  0.490 |  35.6 ms |   45 ms |      1 |            1 |
| 短 prompt（768）  | main |  0.674 |  42.3 ms |  234 ms |     96 |            8 |
| 长 prompt（4864） | V1   |  0.612 |  92.5 ms |   99 ms |      5 |            5 |
| 长 prompt（4864） | main |  1.686 | 309.2 ms | 1985 ms |    480 |           40 |
| 混合              | V1   |  0.657 |  80.4 ms |   84 ms |      1 |            1 |
| 混合              | main |  1.777 | 303.1 ms | 1222 ms |    288 |           24 |

关键比值：

- `main ÷ V1` 的 **ITL max = 5.16× / 20.11× / 14.46×**。
- **ITL p99 = 1.19× / 3.34× / 3.77×**。
- main 的 480 个停顿步、最长连续 40 步 × ≈55 ms ≈ 2.2 s，正对上实测 ITL max 1985 ms。

SARATHI 论文 Fig.2 描述：

- 「effectively eliminates the multi-second generation stalls observed in vLLM」
- 「maintains a significantly lower P99 TBT as the query rate increases」

本表在现象、量级、指标选择上都是同一件事。main 的「整步只做 prefill、decode 完全停摆」正是论文所说的 generation stall。

旁证：vLLM 文档给的两条收益我们都测到了：

- ITL ✓
- GPU 利用率 95.9%、KV 利用率 82.6~86.6% ✓（混合批把两类负载放进同一步）

### 2.3 TTFT：吻合，且能解释为什么没变差

| `main ÷ V1` | TTFT p50 | TTFT p99 | ITL p50 | ITL p99 | ITL max |
| :---------- | -------: | -------: | ------: | ------: | ------: |
| 短          |    1.04× |    1.03× |   1.00× |   1.19× |   5.16× |
| 长          |    1.00× |    1.00× |   0.99× |   3.34× |  20.11× |
| 混合        |    1.03× |    1.02× |   1.00× |   3.77× |  14.46× |

- TTFT 几乎不动（1.00~1.04×），ITL 尾部差 5~20×。
- 与文档「budget 小 → ITL 好 / budget 大 → TTFT 好」以及 SARATHI「prioritizing TBT over TTFT」框架一致。
- 需要解释：SARATHI 是牺牲 TTFT 换 TBT，我们这里 TTFT 连牺牲都没有。
- 原因可算：并发 8 条 seq，每步 decode 只吃 8 个 token，budget 是 1024，挪用比例 8/1024 = 0.78%。
- 实测长场景 TTFT p50 从 35 614 ms 变到 35 477 ms（−0.39%，在噪声内）。
- 我们的 V1 分支没有重排 prefill 推进顺序：每步仍只吃一个 chunk、admit 次序不变；只把「已出 token 的 seq」插进同一步。
- 因此：prefill 吞吐几乎不变 ⇒ TTFT 不变；被改变的是「已出 token 的 seq 能否在 prefill 步里继续出字」⇒ ITL 尾部。

### 2.4 官方文档自己承认的边界，我们实测复现了

vLLM 文档原文：

> 「If `max_num_batched_tokens` is the same as `max_model_len`, that's almost the equivalent to the V0 default scheduling policy (except that it still prioritizes decodes).」

对应实测：

- B 组旧 base（budget 16384 ≥ prompt 4700）→ chunked 机制未激活，两版无差。
- C5 budget 扫描（budget = `max_num_batched_tokens`）：

| budget | V1 步 p999 | main 步 p999 |
| -----: | ---------: | -----------: |
|   1024 |   102.3 ms |      71.6 ms |
|  16384 |   950.1 ms |     744.6 ms |

- budget 自身效应 = 9.29×（V1）/ 10.40×（main）。
- 同 budget 下分支差异只有 1.13~1.43×。
- 文档说的「budget 是 ITL⇄TTFT 的总旋钮」在这里有精确数值印证。

### 2.5 步延迟 P999 与峰值显存：官方没有主张，不参与对照

- vLLM 博客未给 P999 步延迟，也未给显存数字。
- 我们这边：同 budget 下 **步 P999 V1 高 1.13~1.43×**（即更差）；**峰值显存逐位相同（1.0000×）**。
- SARATHI 的「uniform batches 消除 pipeline bubbles」目标是流水线并行（多卡）场景；本机单卡，没有 bubble 可消。
- ⚠「V1 的步更长」不能归因给「混合步牺牲了 CUDA graph」。
  - C6 实测这笔代价只有 **0.3~1.3 ms/步（1.00~1.02×）**，相对 74~112 ms 步长是 1% 量级。
  - V1 步更长是因为一步做的事更多：prefill chunk 与 decode 合并进同一步，而 main 把它们拆成两步。
  - 代价指标应看墙钟 / 吞吐（0.96~1.04×），不要看「步延迟」；两版的「一步」不是同一个工作量单位。

## 3. 混合批 × CUDA Graph：实测、阻塞点、结论修正

### 3.1 C6b：阻塞点二分定位

脚本 `c6b_bisect.py`，每个阶段独立进程（CUDA sticky error 会污染上下文）：

| 阶段                                                                                                        | 结果                   |
| :---------------------------------------------------------------------------------------------------------- | :--------------------- |
| `warm`（只预热 3 次，不捕获）                                                                               | PASS（形状本身没问题） |
| `cap_model`：只捕获 28 层主干（含 FA varlen + prefix cache 的 `block_table` 路径 + triton `store_kvcache`） | PASS                   |
| `cap_logits`：只捕获 lm_head，保持原样                                                                      | FAIL                   |
| `cap_logits` + 静态 gather 索引                                                                             | PASS                   |
| `full`：整步（主干 + lm_head），保持原样                                                                    | FAIL                   |
| `full` + 静态 gather 索引                                                                                   | PASS ✓                 |
| `full` + 静态索引 + `--no-attn`                                                                             | PASS                   |
| `full` + 静态索引 + `--no-compile`                                                                          | PASS                   |

第一现场：

```text
File "nanovllm/layers/embed_head.py", line 60, in forward
    last_indices = last_indices[context.need_logits]
torch.AcceleratorError: CUDA error: operation not permitted when stream is capturing
```

根因：

- 布尔掩码索引在 aten 里走 `nonzero`，需要一次 device→host 计数同步。
- 捕获流里非法。

修法：

- 换成捕获外预计算、形状固定的 1D `int64` gather 索引。
- 即 vLLM 的 `logits_indices` + pad 到桶。
- `--no-attn` / `--no-compile` 都仍然失败，只有换索引才过。
- 说明这是唯一的结构性阻塞，与 attention、与 `torch.compile` 都无关。

值得记一笔：这行代码是用户自己那三项优化里「跳过采样（`need_logits`）」引入的。它同时是「混合步能不能进图」的唯一阻塞。

### 3.2 C6：修完之后值多少

10/10 形状全部捕获成功。同形状、同 buffer、同输入拷贝，`min of 20`：

| 形状                     |    T |    eager |   graph |       省 |  倍数 |
| :----------------------- | ---: | -------: | ------: | -------: | ----: |
| decode×1                 |    1 | 24.63 ms | 5.85 ms | 18.78 ms | 4.21× |
| decode×8                 |    8 |    27.43 |    9.30 |    18.12 | 2.95× |
| chunk32                  |   32 |    25.81 |    5.56 |    20.25 | 4.64× |
| decode×32                |   32 |    28.20 |   20.97 |     7.22 | 1.34× |
| chunk1024（无 prefix）   | 1024 |    40.36 |   39.83 |     0.53 | 1.01× |
| chunk1024 + prefix cache | 1024 |    74.82 |   73.59 |     1.23 | 1.02× |
| mix1024+16               | 1040 |    80.69 |   79.82 |     0.87 | 1.01× |
| mix1024+32               | 1056 |    91.54 |   90.27 |     1.27 | 1.01× |
| mix1024+64               | 1088 |   111.41 |  111.11 |     0.31 | 1.00× |
| chunk4096 + prefix       | 4096 |   365.98 |  364.68 |     1.29 | 1.00× |

![C6](figs/c6_prefill_graph.png)

怎么读：

- graph 消掉的是固定开销 ≈ 19 ms/步（kernel launch + CPU 侧），与 T 无关。
- GPU 计算量随 T 线性增长。
- T ≤ 32：计算填不满 19 ms → 省 7~20 ms（1.34~4.64×）。这是 piecewise / FULL 真正服务的区间；官方文档也写 FULL 适合「小模型或小 prompt 的工作负载」。
- T ≥ 1024：单步 GPU 要 40~366 ms，launch 已被掩盖 → 只剩 1%。真实混合步就在这里。

### 3.3 与 C3 的口径冲突及裁决

- C3 曾报「混合步 decode 比 graph 多花 5.77 ms（D=32）」。
- 那是把 D 条 decode 单独喂进通用分支测出来的，那一批 T 只有 32，正落在「固定开销主导」区间。
- 把它外推到 T≈1050 的真实混合步不成立。
- C6 直接测真实形状 → 0.3~1.3 ms/步（1.00~1.02×）。

裁决：

- 原 §2 结论「vLLM 把 chunked prefill 的代价压到几乎免费，我们这里要算账」作废。
- 改为：混合步走 eager 只贵 1%，这件事我们本来就不算账。
- C5 里「V1 步 P999 高 1.13~1.43×」也因此不能归因给 graph。
- 那是「一步做的事更多」（prefill chunk 与 decode 合进同一步），不是「少了 graph 减免」。

### 3.4 附带发现：固定形状下 attention 其实可以进图

- 官方说「attention 非图安全」。
- 但 `cap_model` 明确 PASS：`flash_attn_varlen_func`（含 `block_table` prefix-cache 路径）+ `store_kvcache` triton kernel，在固定形状下都能被录进图并正确 replay。
- 差别在前提：
  - vLLM 要在同一张图里服务多种形状（分桶复用），所以必须把 attention 摘出去。
  - 我们的方案是每个桶各录一张，形状恒定，attention 就能留在图内。
- 这说明「要不要 piecewise」不是技术约束问题，而是收益/成本问题。
- 在我们的负载下收益只有 1%。

### 3.5 真正该抄的是什么

C6 顺带证明：固定形状下，FA 2.8.3 的 varlen attention 可以被录进图。

差距不在「能不能录图」，而在 C3 表里剩下那 4.29 ms：

```text
t_d_generic（通用分支，D=32）  29.974 ms
t_d_eager  （decode 分支，D=32）25.687 ms      ← 差 4.287 ms = 74% 的「税」
t_d_graph  （decode 分支 + graph）24.207 ms     ← graph 只占 1.48 ms = 26%
```

- 混合步里 decode 行的真正代价是「走了 varlen + 整 cache 的 attention 路径」，不是「没走 graph」。
- vLLM 用一个统一 attention 算子按 metadata 分组派发后端：prefill 组走 varlen / cascade、decode 组走 paged decode kernel。
- 这才是我们该抄的那一条。
- 具体做法见本文 §5 Tier 1。

## 4. 差距清单：真要抄，缺什么

| 能力                                   | vLLM V1                                         | nano-vllm（V1 分支）                                                                                                       |
| :------------------------------------- | :---------------------------------------------- | :------------------------------------------------------------------------------------------------------------------------- |
| 统一扁平批                             | `{req_id: num_tokens}` + 张量化元数据           | 已有：`prepare_prefill()` 已经是「扁平 token 列表 + `cu_seqlens` + `slot_mapping`」，decode 行以 `seqlen_q=1` 混在同一批里 |
| 形状静态化                             | `cudagraph_capture_sizes` + pad 到桶 + dummy 行 | 缺。`is_uniform` 只有 True/False 两态，没有「按 T 分桶 + padding」机制                                                     |
| 图内 token-wise 段                     | piecewise（attention 出图）                     | 缺。`run_model()` 是「要图就整步进图、要 eager 就整步 eager」                                                              |
| 图外 attention 的 buffer 归图所有      | attention 出参化                                | 缺；但按 §3.4，我们不需要这条                                                                                              |
| `cudagraph_unsafe` 标记 / 图切分自动化 | inductor graph partition                        | 缺；手写切分也做得了                                                                                                       |
| 运行时按批组成派发                     | dispatcher + 5 档模式                           | 缺。`llm_engine.step()` 的 `is_uniform` 是最粗糙的一档                                                                     |
| decode 行的 attention 后端选择         | `unified_attention` 按 metadata 分组派发        | 缺，且这是最贵的一条（§5 Tier 1）                                                                                          |

## 5. 优化路线（按性价比排序）

### Tier 0：静态 `logits_indices`（必做；约 10 行；零风险）

改动：

1. `nanovllm/utils/context.py`：`Context` 增加 `logits_indices: torch.Tensor | None = None`。
2. `nanovllm/engine/model_runner.py::prepare_prefill()`：`need_logits` 和 `cu_seqlens_q` 本来就是 Python list，直接在 CPU 侧算全局行号，零同步、零额外算子：

```python
idx = [cu_seqlens_q[i + 1] - 1 for i, need in enumerate(need_logits) if need]
pad = (-len(idx)) % 8                      # pad 到 8 的倍数：形状固定，且是 capture 桶的雏形
idx += idx[-1:] * pad if idx else []
logits_indices = torch.tensor(idx, dtype=torch.int64, pin_memory=True).cuda(non_blocking=True)
```

3. `nanovllm/layers/embed_head.py::ParallelLMHead.forward()`：`if context.is_prefill: x = x[context.logits_indices].contiguous()`。
   `postprocess()` 继续用原来的 bool `need_logits` 对账（Python list，不受影响）。

收益：

- 消掉每个 prefill 步的一次 `nonzero`（device→host 计数同步）。
- 混合步立刻变得可捕获（为将来留口）。

代价：

- pad 出来的重复行会多算几行 lm_head（≤7 行 × vocab，可忽略；C4 已测官方口径下 lm_head 行数差异 ≈0.04%）。

验收：

- A 组正确性对比（token 逐位相同）。
- B 组三场景复跑，确认 ITL / TTFT 不变或更好。

### Tier 1：统一 attention 按 query 长度分组派发（收益最大；预期 ~4.3 ms/步）

证据（C3，D=32，同为 eager、只差 attention 路径）：

```text
t_d_generic（通用分支：decode 行也走 varlen）  29.974 ms
t_d_eager  （decode 分支：paged decode kernel）25.687 ms   ← 差 4.287 ms = 74% 的「税」
t_d_graph  （decode 分支 + graph）             24.207 ms   ← graph 只占 1.48 ms = 26%
```

相对 `mix1024+32` 的 91.5 ms 步长 ≈ 4.7%/步，是 Tier 2 的 3.4 倍。

为什么现在是这样：

- `Attention.forward()` 只看 `context.is_prefill`。
- 混合步整批 `is_prefill=True`，于是 decode 行（`seqlen_q == 1`）也被塞进 `flash_attn_varlen_func`。
- 存在 prefix cache 时 `block_tables is not None` → `k, v = k_cache, v_cache`，等于对整个 KV cache 池做 varlen gather。

改法：对齐 vLLM 的 `unified_attention`，但用手工坐标切片实现。

关键有利条件：

- `schedule()` 顺序：先跑 running（decode）再跑 waiting（prefill）。
- `prepare_prefill()` 严格按 `seqs` 顺序拼接。
- 所以一步之内 decode 行是前 `nd` 行的连续区间、prefill 行是后 `T-nd` 行的连续区间，天然可切。

```python
nd = number of decode rows           # 新增：prepare_* 里记进 context
if nd == 0:                          # 纯 prefill / 纯 decode：走原路径，零额外成本
    ...
else:                                # 混合步：两段各走各的后端
    o_dec = flash_attn_with_kvcache(q[:nd].unsqueeze(1), k_cache, v_cache,
                                    cache_seqlens=ctx.context_lens[:nd],       # 新增：decode 段的 K 长度
                                    block_table=ctx.block_tables[:nd], causal=True)
    o_pre = flash_attn_varlen_func(q[nd:], k_pre, v_pre,
                                   cu_seqlens_q=ctx.cu_seqlens_q_pre,          # 新增：减去 nd 偏移
                                   cu_seqlens_k=ctx.cu_seqlens_k_pre,
                                   max_seqlen_q=ctx.max_seqlen_q, max_seqlen_k=ctx.max_seqlen_k,
                                   causal=True, block_table=ctx.block_tables_pre)
    o = torch.cat([o_dec.squeeze(1), o_pre])
```

需要新增的元数据（都在 `prepare_prefill()` 里一次算好，CPU 侧、零同步）：

- `n_decode_rows`
- `context_lens`（decode 段）
- `cu_seqlens_*` / `block_tables` 的 prefill 段视图

验收（按门禁走）：

1. 激活门：可观测混合步数与 `nd`，确认分段确实发生（`nd > 0` 的步占比）。
2. 对称门：建议只改 V1，把它当成 V1 的第二个优化项，与 main 对比时明确「V1 = 混合调度 + chunked prefill + 分组 attention」。
3. 容量门：池约束 + 抢占=0。
4. 判据门：主判据 = 混合步的步延迟 p99/p999 与 ITL p999，并并列报告停顿步数（频率量）。
5. 正确性：A 组 token 逐位对比必须通过（`cat` 的行序必须与 `postprocess` 的消费顺序一致——这是唯一容易错的地方）。

### Tier 2：piecewise CUDA graph（明确不做）

C6 实测：

- T ≥ 1024 时 1.00~1.02×，绝对收益 0.3~1.3 ms/步。

实现它需要：

- 按 T 分桶的桶集合（chunk 固定 1024 时 T = 1024 + D，D 每变一次就多一张图）。
- 每桶 28 层的手工切分。
- buffer 归图管理。
- `need_logits` 之类的动态算子全部静态化。

投入产出比是负的。记录为「已评估、否决」。

唯一会让它重新变成正收益的场景：

- 负载变成「小 prompt / 小 batch / decode 主导」（T ≤ 32）。
- 而那个区间我们已经吃到这份收益了：纯 decode 步本来就整批走图（C3 的 `t_d`，D=1 时 3.15×）。

### Tier 3：长期（可选）

- 桶管理：现在 `graph_bs = [1,2,4,8] + range(16, max_bs+1, 16)` 是按 batch size 分桶（decode 用）。若将来要录 prefill / 混合步，需要一套按 token 数 T 分桶的独立表（vLLM 的 `cudagraph_capture_sizes`）。两套桶语义单位不同，别混用。
- 图安全的 attention 后端 + FULL 模式：自写 triton paged decode kernel（固定 `max_seqlen`）+ 固定形状 varlen，就能像 FA3 那样做整图。但前提收益仍然是「T 小」。

### 反面清单（别做）

- ✗ 别为了「用上 graph」把 chunk 调小：chunk 变小 → T 变小 → 固定开销占比上升，graph 的账面收益确实变大，但那是「把账做小」而不是「把事做快」；总步数上升，端到端更慢。
- ✗ 别把「步延迟」当优化判据：两版的「一步」不是同一工作量单位（V1 一步 = prefill chunk + decode）。看墙钟 / 吞吐 / ITL 尾部。
- ✗ 别指望 graph 能改善 ITL 尾部：ITL 尾部的病根是相位分离（整步只做 prefill），graph 只影响「每步多长」，不影响「decode 会不会被整步卡住」。

## 6. 总判定

| 维度                   | vLLM 官方主张                                                                    | 我们实测                                                                                                   | 判定                                                                                                                   |
| :--------------------- | :------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------- | :--------------------------------------------------------------------------------------------------------------------- |
| 吞吐                   | V1 vs V0 最高 1.7×（归因 CPU 开销）                                              | 0.958~0.990×                                                                                               | 不吻合，但不构成矛盾——官方 1.7× 来自执行循环重建，我们只改调度器；且官方自陈吞吐最优是 budget > 8192（chunk 近乎关闭） |
| ITL / TBT 尾部         | chunked prefill 核心卖点：消除数秒级 stall、P99 TBT 大降                         | ITL max 1/20；停顿步 480→5，最长连续 40→5                                                                  | 强吻合（现象、量级、指标选择一致）                                                                                     |
| GPU 利用率             | 混合批提高利用率                                                                 | 95.9%（显存控制器 96.3%）                                                                                  | 吻合                                                                                                                   |
| TTFT                   | 小 budget 牺牲 TTFT 换 ITL                                                       | 1.00~1.04×（几乎不变）                                                                                     | 吻合且可解释——挪用比例仅 8/1024 = 0.78%                                                                                |
| budget ⇄ ITL/TTFT 权衡 | 文档明写 budget 是总旋钮；budget == max_model_len ≈ V0 默认策略                  | budget 效应 9.29~10.40×；同 budget 分支差异 1.13~1.43×；budget=16384 时退化                                | 逐字吻合                                                                                                               |
| 步 P999 / 峰值显存     | 官方未主张                                                                       | 步 P999 V1 高 1.13~1.43×；显存逐位相同                                                                     | 不参与对照（SARATHI 的 uniform batch 是为 PP 消 bubble，单卡不适用；「步更长」是因为一步做的事更多，见 §2.5）          |
| 混合批 × CUDA graph    | V1 用 piecewise/FA3 让混合批不牺牲 graph；官方点名 FULL 模式适合小模型/小 prompt | 混合步整步 eager 的代价实测 0.3~1.3 ms/步（1.00~1.02×）；T≤32 区间 graph 值 1.34~4.64×，而那里我们已经走图 | 不吻合但无需吻合——piecewise 服务的是 launch 主导的小 T 区间，长 prompt 混合步里它只值 1%                               |
| SLO 下服务容量         | SARATHI：2.6× / 3.7× / 5.6×                                                      | 未测                                                                                                       | ⚠ 唯一真实缺口，见 §7                                                                                                  |

一句话回答：

- 机制层面吻合得相当好；吞吐数字不吻合且本来就不该吻合。
- 「混合批 × CUDA graph」这条我们曾经以为的差距，实测下来只有 1%。
- 我们复现的是 vLLM V1 的调度器那一半：统一调度 + decode 优先 + chunked prefill + 跨步维护增量 KV。
- 它兑现的正是官方文档与 SARATHI 给 chunked prefill 派的那两件事：尾延迟与 GPU 利用率。
- vLLM V1 的 1.7× 是执行循环那一半的功劳：多进程 EngineCore、持久输入、torch.compile、piecewise CUDA graph、prefix caching。那部分我们没做、在本仓也没有对应杠杆。
- 其中 piecewise CUDA graph 经 C6 实测确认：在我们的负载形状下只值 1%，不构成差距。

待办优先级：

1. SLO 下服务容量（§7，唯一真实缺口）。
2. 统一 attention 按 query 长度分组派发（C3 里 74% 的混合步 decode 代价在这里，见 §5 Tier 1）。
3. 静态 `logits_indices`（顺手的零成本改动）。
4. ~~piecewise CUDA graph~~（已否决）。

## 7. 唯一真实的缺口：SLO 约束下的服务容量

SARATHI 的 2.6× / 3.7× / 5.6×：

- 不是「固定工作量下比墙钟」。
- 而是「给定 P99 TBT ≤ SLO，系统能扛多大请求速率」（capacity under tail-latency constraints）。

现有实验口径：

- C1 stress / C1 ctrl / C0 bench 都是固定工作量口径。
- C1 ctrl 下两版 prefill / decode token 逐位相同（差 −1 / −0），结构上不可能测出容量差异。
- 因此这条不是「结论冲突」，而是度量轴不同 + 该轴未测。

要补它，需要新的实验形状（现无脚本）：

1. 泊松到达 + 固定速率，扫 RPS（例如 2/4/6/8 req/s），每档跑够稳态时长。
2. 对每档记录 P99 ITL（或 P99 TBT）。
3. 画「RPS → P99 ITL」曲线，取 P99 ITL ≤ SLO（如 200 ms / 500 ms）的最大 RPS。
4. 两版在同一 SLO 下的最大 RPS 之比 = 可以直接对标 SARATHI 的 2.6× 的那个数。

预期方向（基于现有数据的推断，尚未实证）：

- 两版吞吐几乎相同（0.96~0.99×）。
- V1 的 ITL 尾部好 5~20×。
- 在严格的 ITL SLO 下，V1 的容量应显著更高；SLO 越松，两者越接近。
- 这也正是「这个优化是低并发 / 长 prompt / 流式交互的优化，不是高并发吞吐优化」这句话的定量版本。

```bash
cd ~/projects/nano-vllm && export PYTHONPATH=$PWD TQDM_DISABLE=1

CUDA_LAUNCH_BLOCKING=1 .venv/bin/python experiments/c6b_bisect.py --stage full --raise

# 出图
~/venvs/fig/bin/python experiments/c6_fig.py     # -> experiments/figs/c6_prefill_graph.png
```

踩过的坑（供后续复用）：

1. 块表必须落在 `config.num_kvcache_blocks` 内：本机 Qwen3-0.6B（28 层 / 8 KV heads / 128 head_dim / fp16）每块 29.4 MB，`gpu_memory_utilization=0.8` 时只有 148 块。构造测试批时块号越界 → `store_kvcache` 写飞 → illegal memory access。
2. 直接调 `runner.model(...)` 必须包 `torch.inference_mode()`：仓库里 `activation` / `rotary_embedding` / `layernorm` 挂了 `@torch.compile`，在 grad 模式下 AOT autograd 会在 `silu_and_mul` 的 inplace 上报错。
3. CUDA 的 sticky error 会污染上下文：捕获一失败，后面所有数字都不可信——每个阶段用独立进程（`run_c6b*.sh`）。
4. `import torch._dynamo` 写在函数里会把 `torch` 变成函数局部名 → `UnboundLocalError`；用 `import torch._dynamo as _dynamo`。
