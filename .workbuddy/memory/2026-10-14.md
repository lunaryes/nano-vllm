## TPOT 抖动来源分析（回答「离线能否验证流式平滑性」）

用户追问：混合调度除长序列外是否还为了流式对话的平滑性？离线推理里是不是只有抢占重 prefill 才会导致 TPOT 抖动？

### 产出
- 新增 `experiments/b4_jitter_decomp.py`（步级抖动来源分解）→ `results/b4_jitter_decomp.md`
- 新增 `experiments/抖动来源与实验效度.md`

### 关键实测结论（`b3_*.json` r1）
- **两版抢占均为 0**，但 main 仍有 88/88/66 段停滞，占墙钟 **14.6%/35.6%/28.5%**；V1 各仅 1 段（冷启动，0.1~0.4%）。→ **抖动不需要抢占**。
- **主因是「相位分离」**：main 的 `schedule()` 只要 waiting 非空就整步做 prefill、**decode 段完全不执行** → nd==0 停滞步 96/480/288（= 96 条 × 1/5/3 chunk）。ITL max 231/1984/1219 ms；long 场景最长连续 40 停滞步 × 55.8 ms ≈ 2.2 s，与 ITL max 1984 ms 自洽。
- **三场景 ITL p50 两版逐位相同**（9.0 / 24.8~25.1 / 17.9）→ V1 **不改中心只削尾部**。「不是更快，而是不卡」。
- main 也受 budget 约束、prefill 同样被切成 chunk（480 步 = 96×5）——它的问题不是「没切」，而是「切了之后整步只做 prefill」。
- **抖动 4 类来源**：① 相位分离（离线可测、主因）② 混合步自身成本 `T_prefill+T_decode`（可测）③ 抢占重 prefill（可测但可锁池归零）④ 新请求到达（**离线结构性缺失**）。
- **效度边界**：离线对「流式平滑性」**必要不充分** —— 能证机制有效，不能给真实到达率下的 TPOT 尾部。补齐路径：中途注入（低成本）/ 泊松到达仿真（可对外给数）。
- 反直觉点：若 N ≤ 并发上限（无 waiting 积压），两版完全相同、**只剩抢占能造抖动**——但那种配置下第 1 类来源不存在，实验也就测不到任何信号。

## 代码级澄清：相位分离的根源与 ITL 的构成（用户质疑「TPOT 是 decode 间隔，与相位分离何干」）

### main 相位分离的**唯一根源**（`nanovllm/engine/scheduler.py`）
```python
# prefill 段：只处理 waiting[0]，切 chunk 填满 budget
while self.waiting and len(scheduled_seqs) < self.max_num_seqs: ...
if scheduled_seqs:
    return scheduled_seqs, True     # ←← 一旦 admit 到任何 seq，立刻返回；decode 段完全不执行
# decode 段（只有 prefill 段一个都没 admit 到时才走到）
while self.running and ...: ...
return scheduled_seqs, False
```
- 每步**只 prefill waiting[0] 的 1 个 chunk**（1024 token，`remaining` 立刻归 0）→ 长 prompt 5 chunk 要 5 个连续步完成。
- 池满时 `can_allocate` 返回 -1 → break → prefill 段空 → 才走 decode。故 main 的步序列形态为
  `[35 步纯 prefill][N 步 decode][5 步 prefill][M 步 decode]…`，**形状由「池何时腾出空位」决定**。
- V1 相反：`running` 段先跑（decode 每步 1 token / chunked prefill 吃剩余预算），**同一步内混合**。

### ITL 不成立的推理链
- ITL(两次 token 产出) = **该区间内所有调度步的墙钟之和**，**不等于**「decode 步的执行时长」。
- main 的 decode 步本身只 ~25 ms（long 场景），但两步之间插了 35 个 55.8 ms 的纯 prefill 步 → ITL = 35×55.8+25 ≈ 1978 ms。
- 即：**不是 decode 变慢，而是 decode 那一步根本没被调度**（seq 仍在 running、KV 未释放、未被抢占）。
- 正确条件：平滑的前提是 **waiting 为空（无排队积压）**，而不是「无抢占」。「无抢占」= 池够；「waiting 空」= 无排队，后者强得多。本实验满足前者（抢占 0）不满足后者（N=96 ≫ 并发 7）。
- 设计动机：main 必须整步二选一，否则 decode 上不了 CUDA graph（prefill 走 eager）。V1 混合步的代价正是混合批里的 decode 也走 eager（C0 的 5.88% decode token）。
- 另注：**TPOT 是平均值**（(E2E−TTFT)/(n−1)），会掩盖抖动；两版 p50 逐位相同（24.8 vs 25.1 ms），差异全在尾部。

### 关键补充：相位分离影响 ITL 的**充要前提是「admit 串行」**
- 用户两度质疑「相位分离怎么会影响 TPOT？相位分离下 TPOT 明明很好」——**在 decode 相位内部确实很好**（long 25.8 ms/步、short 8~9 ms/步，与 V1 相同）。
- 但**seq 不是同时 admit 的**：budget 一步只装得下**一条** seq 的一个 chunk。main/long 实测前 46 步：
  - 步 1~5 = seq1 的 5 chunk（1024×4+606）→ **seq1 在步 5 产出 token#1**
  - 步 6~10 = seq2，步 11~15 = seq3 … 步 36~40 = seq8 → **seq1 全程在 running 却一步都轮不到**
  - 步 41 = 池满 `can_allocate` 失败 → 才进 decode → **seq1 产出 token#2**
  - → seq1 的 ITL = 36 步 × ~57 ms ≈ **2052 ms**（实测 max 1984 ms ✓）
- short 场景同理：步 1~8 各装一条（每条 prompt ≤ budget，一步 prefill 完），步 9 才 decode → seq1 的 ITL ≈ 8 × 31.8 = 254 ms（实测 231 ms ✓）；此后每完成一条腾出块就再插 1 步 prefill。
- **用户直觉隐含的前提**：「所有 seq 同时进入同一相位」= budget ≥ 一批请求的总 token 数。**这正是旧 base 场景（budget 16384）测不出收益的原因** —— 一步装完整批，此后全程 decode，相位分离代价归零。
- **精确表述**：不是「相位分离影响 TPOT」，而是「**当 budget < 一批请求总 token 数时，prefill 被迫串行展开，相位边界就落进了别人的 decode 里**」。代价 ∝ prefill 步数 × 步时长 × 等待中的 decode seq 数。

## 指标归属澄清：相位分离的代价记在 ITL，不记在 TTFT（用户质疑「这不该用 TTFT 测吗」）

### 实测证据（新增 `experiments/b4_ttft_vs_itl.py`，三场景 r1，比值 = main ÷ V1）
| 场景 | TTFT p50 | TTFT p99 | TTFT max | ITL p50 | ITL p99 | ITL max |
| :--- | ---: | ---: | ---: | ---: | ---: | ---: |
| 短 | 1.04× | 1.04× | 1.03× | 1.00× | 1.19× | **5.04×** |
| 长 | 1.00× | 1.00× | 1.00× | 0.99× | 3.32× | **20.35×** |
| 混合 | 1.03× | 1.02× | 1.02× | 1.00× | 3.79× | **14.32×** |

首 token 出现的调度步（表 3）：short V1 第 2 步 / main 第 9 步；long V1 第 6 步 / main 第 41 步；mix V1 第 2 步 / main 第 25 步。

### 结论（核心）
- **TTFT 两版逐位相同（1.00~1.04×）→ 相位分离在 TTFT 上零痕迹**；差异全部落在 ITL 尾部。
- 根因：**TTFT 窗口在首 token 处关闭**。同一段 GPU 时间（步 6~40）对 seq1（步 5 已出 token）记入 **ITL**，对 seq8（步 40 才出 token）记入 **TTFT**。指标归属取决于「该 seq 首 token 是否已产出」。
- 为什么 TTFT 相同：两版**总 prefill 工作量与串行排布方式相同**（V1 每步也只吃一个 chunk）→ 第 k 条 seq 的 TTFT 由「前 k−1 条的总 prefill 量」决定，两版一样。V1 改变的不是排布，而是「已出 token 的 seq 能否在 prefill 步里插进去」。
- **指标瓶颈分工**：TTFT ← prefill **吞吐**（chunked 几乎不动）；ITL/TPOT 尾部 ← prefill 与 decode 的**交织方式**（chunked 的战场）。**只盯 TTFT 会完全看不到该优化的价值。**
- 一句话：TTFT = 「你多久开始说话」，ITL = 「你说话是否连贯」。main 让 seq1 在步 5 开始说话、然后哑 2 秒——这 2 秒只能记在 ITL 上。
