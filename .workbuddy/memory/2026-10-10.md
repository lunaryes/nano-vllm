## 讨论（续 10-09）：混批下「时间分不开」——本质结论与出路
- 学生的疑问：已经分开了 prefill / decode 的 token 计数，但**处理时间是混在一起的，无法分开**。
- **结论：他的观察是对的，而且是原理性的**——混批下一步 forward 把两类 token 同时喂给同一批 kernel，`step_time` 只是一个数，**batch 级时间不可分解**（不能用代码修）。
- **出路是换粒度**：
  1. **批级只能得到**：`Σprefill_tokens / elapsed` 与 `Σdecode_tokens / elapsed`。两者是「**同一段墙钟上、两种工作各自完成多少**」的 workload-average 速率，都被对方稀释；它们的和 = 总吞吐。vLLM 的 `avg_prompt_throughput` / `avg_generation_throughput` 就是这么算的（分子分开计数、分母同一个 elapsed）。**可以用于容量规划，但不是「纯 regime 速率」。**
  2. **请求级天然可分**：单条请求的时间线是「先 prefill、后 decode」**顺序分期**，跨请求才混合。→ **TTFT** = 首 token 时刻 − 到达时刻（含排队）；**TPOT** = (结束 − 首 token)/(生成数 − 1)。这是**唯一真正可分离**的时间量。
  3. **估算型**：记录每步三元组 `(prefill_tokens, decode_tokens, step_time)`，回归 `step_time ≈ α + β·prefill_tokens + γ·decode_tokens`（直觉：decode 成本近似为「常量」(权重+KV 带宽，与 batch 弱相关)，prefill 成本随 token 数线性）。近似、需足够负载变化。
  4. **物理分离**：只测「纯 decode 步」的 step_time 来估 decode 速率（混合步不计入速率）；或 **P/D 分离**（各实例只跑一种 regime，速率无歧义）——工业界对「混批测不准」的终极答案。
- **同一根因第三次回响**：batch 级标量表达不了批内异构 → ① 调度器的 bool→per-seq `is_prefill`；② lm_head 的 bool→per-seq 掩码；③ **指标：批级时间不可归因 → 改用 per-request 延迟（TTFT/TPOT）**。
- **实践提醒**：先测量「混合步占比」。nano-vllm 默认 `max_num_batched_tokens` 较大时，离线 bench 常常第 1 步是纯 prefill、其后多为纯 decode，**混合步可能很少** → 时间归因问题在多数步上并不存在；真发生时把该步标为 "mixed" 即可。
- 仍挂起（10-09 已记）：`llm_engine.py:52` 符号反转、`generate()` 的 `if num_tokens > 0` 依赖旧符号语义；warmup `self.run(seqs, True)` 应改 `is_uniform=False`。

## 讨论：bench.py 是不是离线吞吐基准

- 三个要点：
  1. 分子只数**输出** token、不含 prompt token，分母却含 prefill 时间 → 是"**混合负载下的输出吞吐**"，被 prefill 拉低；**只宜同 workload 的 before/after 对比**，不宜跨实现比绝对值。

  3. 由此印证"**先测量**"：本负载下"时间不可分"只涉及 ~9 步，不值得投入工程。
- 引导问题：混合调度 + chunked prefill 生效时该数应**变大**（不让长 prefill 阻塞 decode）；是否要在 bench 里同时数 prompt token（决定能否与 vLLM `benchmark_throughput` 定义对齐）。

## 讨论：为什么吞吐量每步（每 batch）都算一次
- 学生当前 `generate()`（已改成 `num_tokens_prefill/num_tokens_decode` 两个数）里 `prefill_throughput = np/(perf_counter()-t)`、`decode_throughput = nd/(perf_counter()-t)`，每轮循环算一次。
- **答案：这是"显示需求"，不是吞吐量的定义要求。** `tqdm.set_postfix` 每轮都要刷新 → 顺手每轮算一次。吞吐量 = `tokens / Δt`，**Δt 是可选窗口**：单步（现用）/ 滑动或 EMA / 全程累计（bench 用的）。
- 每步算一次的三个代价：① **噪声**（单步抖动全进分母）；② **混批下不成立**（两个数共用同一分母，既非 prefill 速率也非 decode 速率）；③ **计时范围污染**：`t = perf_counter()` 包住整个 `self.step()`，含 `schedule()`（纯 CPU）、`prepare_*`（Python 循环建 list + `torch.tensor(pin_memory=True).cuda()` 的 H2D 拷贝）、`postprocess`、outputs 构造 —— **batch 越小 CPU 占比越高**。真正的"算 token"只占一部分。
- 代码细节：`run()` 里没有显式 `torch.cuda.synchronize()`，但 `self.sampler(logits, temperatures).tolist()` 的 **`.tolist()` 就是隐式 D2H 同步点**（所以 per-step 时间确实包含了 GPU 前向，不是纯 CPU launch 时间）。另：`perf_counter()` 被调了两次（两个数分母不同，应 `dt = perf_counter()-t` 只算一次）；两个吞吐变量每轮**被覆盖** → 进度条显示的是"最后一步"的数。
- 建议方向：给人看的数用**累计/EMA**；排查单步用 per-step 但只写日志；要测"模型算力"就把计时缩到 `run()` 前后。vLLM 也是按**时间间隔**打日志（区间累计），不是按单步。
- 引导问题抛给用户：Δt 里有大量 CPU 开销时那还能叫"prefill 吞吐"吗；进度条好看 vs 能对比实验，对窗口的要求是否不同。

## 讨论：那两个分项速率该叫什么 + bench 要不要改
- **命名结论**：`num_tokens_prefill/dt` 与 `num_tokens_decode/dt` **只有在纯净步上**才是各自的"吞吐"。在混合步上它们只是"**本步分项完成速率**"（两类 token 共用同一 `dt`），且**相加 = 该步总吞吐** → 拆开报与"**总吞吐 + 构成比例**"信息量**完全等价**。误读风险：`decode = 3/12ms = 250 tok/s` 会被读成"decode 只能跑 250 tok/s"（实际是"这 12ms 里 decode 只完成 3 个"）。
- **建议**：进度条改报「总 tok/s + `P:D` 构成比」；若保留两个分项，命名要写清"每步/共用分母"。同时把 `perf_counter()` 只调一次（`dt`）。
- **bench.py 要不要改 → 不需要**，两个理由：① 它 `use_tqdm=False` 且**完全不消费 `generate()` 的返回值**（只 `time.time()` 包住 `llm.generate`），`step()` 返回三元组不影响它；② 它算的是**外部固定指标**（`Σmax_tokens / 端到端墙钟`），正是做 before/after 对比想要的"裁判"。**别把 per-step 指标塞进 bench.py。**
- 注意点：bench 分子 `sum(sp.max_tokens)` 精确成立**仅因 `ignore_eos=True`**（每条恰好生成 max_tokens）；若改成 False 就会错。若要报"总 token 吞吐"以对齐 vLLM `benchmark_throughput`，才需要把 prompt token 数加进分子（属于**增补**而非修 bug）。

## Review：混合调度 + chunked prefill 完成度检查（读全仓后）
**已完成且正确的四层**：
1. `scheduler.schedule()`：running 优先（先 running 后 waiting），running 内 decode 分支与 chunked-prefill 分支并存；waiting 按预算先到先收。→ 真正的混合批 + chunked prefill。
2. preempt 逻辑已正确（自 evict 用 `req_idx==len(running)-1` 判定 + `pop()` + `break`；victim 用 `pop()` 尾取），`while...else` 把 commit 绑在"成功"上。
3. `llm_engine.step()`：`is_uniform = all(not seq.is_prefill)`；`run(seqs, is_uniform)` → 纯 decode 走 `prepare_decode`，其余走 `prepare_prefill`（统一 varlen）。
4. `attention.forward` 单路（`context.is_prefill` 选 varlen/with_kvcache）；`ParallelLMHead` 用 `cu_seqlens_q[1:]-1` 取每 seq 末 query；`postprocess` per-seq 判 append。`chunked-prefill 不需要 may_append`（块在 waiting 阶段按整段 prompt 分好）✓。
5. `model_runner.run_model`：`not is_uniform or enforce_eager or size>512` → eager，否则 graph。纯 decode 批仍走 graph ✓。

**P1（真实洞，未解决）——decode 判据的不变式依赖抢占行为**：
- 正常路径下 `num_cached_tokens ∈ {num_tokens-1, num_tokens}`（append 只在 `num_cached>=num_tokens` 时发生），故 `num_cached >= num_prompt` ⟺ `num_cached >= num_tokens-1`，两种写法等价。**但 `deallocate()` 会把 `num_cached_tokens` 置 0，重入时 `allocate()` 又把它设成 `num_cached_blocks*block_size`（前缀缓存决定，≠ num_tokens-1）**→ 不变式破裂。
- 于是：一条**已生成过 token** 的 seq 被抢占后重入，若 `num_cached` 跨过 `num_prompt` 但未到 `num_tokens-1`，running 循环的 `num_cached>=num_prompt` 会为真 → 走 decode 分支 → `prepare_decode` 的 `context_lens=len(seq)=num_tokens`，但实际只存了 `num_cached` 个 → **读到脏 KV，输出错**。
- 触发条件：重入的 seq 的"重算 chunk"被预算截断（`token_budget` 已耗尽）。默认 `max_num_batched_tokens=16384 ≥ max_model_len=4096` 时，重算总能在一步内完成 → **不可达**；一旦把预算调小（正是测试 chunked prefill 的做法）就可达。
- 更安全的判据：`seq.num_cached_tokens >= seq.num_tokens - 1`（即 `num_tokens - num_cached <= 1`）——它直接表达"只剩最后一个 token 没算"，正是 `prepare_decode` 的真实前提。
- 诊断手段：在 `prepare_decode` 开头加 `assert seq.num_cached_tokens == len(seq) - 1`（≤5 行），可把这类洞变成立刻报错。

**P2（浪费，未做）**：混合批走 `prepare_prefill` 时，`ParallelLMHead` 对**每条** seq 都取末 query 算 vocab 投影，包括 mid-chunk（算完就扔）。参考仓库/v1 用 per-seq 掩码 `len(seq)==num_cached+num_new and seq.block_table` 排除。
**P3（策略，未做）**：vLLM 的"本步有抢占就不再收新请求"守卫（`if not preempted_seqs`）；以及 running 内**公平性**——现在按 running 顺序处理，一个长 chunk 可吃掉整段预算，饿死后面的 seq（vLLM 先给各 running 各 1 token 再分块）。
**P4（显示）**：进度条 per-step 分项速率（见上一节）。
**P5（边界）**：末尾 `assert scheduled_seqs` 在"running 全被抢占 + waiting 头分配失败（超池长度）"时会炸，属配置问题。

**建议的验证方式**：① 用 `temperature=0`（贪心）+ 固定 prompt，对比"原版相位分离调度"与"新混合调度"的输出 token ids（batching 舍入允许极少数差异，大量系统性差异即 bug）；② 在 `prepare_decode` 加断言直接守不变式；③ 把 `max_num_batched_tokens` 调小到 < `max_model_len`（否则 chunked prefill 几乎不会被触发），并制造长 prompt + 高并发来逼出抢占。

## 补充问答（学生三问）：lm_head 白算 / 抢占后不收新请求 / 指标 P4 已做
- **lm_head 白算（P2 细化）**：`layers/embed_head.py:58-60`，prefill 路径下 `last_indices = cu_seqlens_q[1:]-1` → 对**每条** seq 取"本轮最后一个 query"做一次 `F.linear(hidden, vocab)`。hidden states 是 Σq 行（必算，prefill 要为每个 token 写 KV）；lm_head 只取每 seq 末 query。decode seq 的这行有用；**mid-chunk prefill seq 的这行是 prompt 中间 token，logits 无人消费**（`postprocess` 因 `num_cached<num_tokens → continue`），于是白付一次 vocab 投影 + 一次采样。**非正确性问题**（全算 → `zip(seqs,token_ids)` 对齐 OK），纯浪费。省它必须引入 per-seq 掩码 → index 会错位 → lm_head/postprocess 都要按掩码索引（v1 做法）。
- **抢占后不再收新请求（P3 依据，已查证）**：vLLM V0 原话 "If any sequence group is preempted, do not swap in any sequence group. **because it means there's no slot for new running requests.**"；V1 抢占动作 = `num_computed_tokens=0` + `waiting.prepend_request(preempted)`（放队首，同轮可被重新捞回）。含义：抢占=运行集已超 KV 容量，**腾出的 block 是留给被踢者重算的，不是给新请求**。若边踢边收 → 新 prefill 又吃满 → 再踢 → 被踢者丢进度重算 → **活锁/抖动**。守的不变式：**发生抢占的这一步，running 规模不许变大**。学生"踢掉后确实多了 block，应该能再放"的直觉只对了一半——空间是留给被踢者的。nano-vllm 量级属**健壮性改进、非正确性修复**。
- **指标 P4：学生已改**（`total_throughput=(np+nd)/dt` + 进度条显示 P/D 构成）→ 上一轮把它列为"未做"是**基于旧版本**，应划掉；符号反转随该版一并消失（不再用正负号编码）。剩余小点：① 仍是 per-step 瞬时值（变量名 total 但每轮覆盖），真要总吞吐应在循环结束后算一次；② `dt` 仍含 schedule/prepare 的 CPU 与 H2D 开销；③ `int()` 冗余。
- 状态：P1（decode 判据改 `>= num_tokens-1`）仍是唯一必须修的真洞，学生尚未动手。

## 追加：学生对「抢占守卫」的质疑（会不会浪费容量）
- 学生观点：踢出好几块、够后续请求用，却因守卫跳过 → 浪费。**答：核心概念要纠正 —— 抢占腾出的块不是「空闲容量」，是「从被抢占者手里借的容量」**。抢占不减少总需求，只换持有者；被抢占者被 `prepend_request` 到 waiting 队首，下一步就要把块要回去。故"够后面的请求用"实为"先把 B 的块给别人用"，B 立刻来要 → 再踢 → 新请求白算 prefill → 抖动/活锁。
- **代价不对称**：守卫代价 ≤ 1 步的接纳延迟（几 ms，且请求下一步就进）；不加守卫的代价 = 每次抢占丢一整条 prompt 的 KV 重算（几十~几百 ms）且可能无界循环。
- **查证（vLLM V1 v0.26）**：`if not preempted_reqs and self._pause_state == PauseState.UNPAUSED:` 才进入 waiting 接纳循环；抢占时 `preempted_req.num_computed_tokens = 0` + `waiting.prepend_request()`。即**被抢占者本步也不重入**。社区总结理由原文："preemption means memory was insufficient for the current population, so admitting more work in the same step would immediately re-trigger preemption churn."
- **诚实补充（守卫确实保守）**：它不检查"是否真有余量"，只用"本步是否发生抢占"作廉价代理；极端情况下（victim 极大、running 需求极小、且被抢占者命中前缀缓存）可能真有被跳过的余量。
- **nano-vllm 特有**：现在 `preempt()` 用 `waiting.appendleft` 且 waiting 循环**无守卫** → 被抢占 seq 在**同一步**被捞回、块立刻复用 → **当前根本没有"空一步"的浪费**；**加守卫才会制造出该浪费**（且会推迟被抢占者 1 步）。故对 nano-vllm，守卫是有真实小代价的取舍，非免费改进。
- **建议**：离线 bench 几乎不触发抢占（`max_num_batched_tokens ≥ max_model_len`，重算一步内完成）→ 守卫在此负载下不触发、谈不上浪费 → **暂不加**，等小 KV 池 + 高并发压测真观察到 thrash 再加。可能的中间方案：只挡"新请求"、仍同轮捞回"被抢占者"（需标记哪些 waiting 项是抢占产生的）。
- 抛给学生的问题：若"踢 1 条、收 3 条"能持续循环，GPU 时间花在哪了？有没有哪个请求的 TTFT 在变小？

## 追加：is_prefill 的真实作用范围 / context 作用域 / 掩码设计
- **学生关键误解（需长期记住并纠正）**：他以为"lm_head 里的 is_prefill 决定是否给每个 token 算 hidden、写 KV"。**错**。事实：
  - **hidden**：`Qwen3Model.forward` 对整批 **Σq 个 token 全算**（embed → N 层 → norm），**与 is_prefill 无关**。
  - **KV 写入**：`Attention.forward` 里 `store_kvcache(k, v, ..., context.slot_mapping)` 在 **if context.is_prefill 之前**执行 → **由 slot_mapping 决定，与 is_prefill 无关**；is_prefill 只决定用哪条 kernel 算输出 o。
  - **全仓 `is_prefill` 只有 2 个消费点**：`layers/attention.py:64`（选 varlen / with_kvcache）、`layers/embed_head.py:58`（选投影哪些行）。
- **`context` 的作用域**：`utils/context.py` 里 `_CONTEXT = Context()` 是**模块级全局单例**，`set_context()` 整体重建、`get_context()` 读。作用域 = **当前进程**（不是"当前 GPU"）。TP 下每个 rank 是独立进程（`mp.Process(target=ModelRunner, ...)`），各持一份。定位：它是"从 model_runner 穿过所有 nn.Module 的隐式数据通道"（因 forward 签名不能随便加参数）。
- **`cu_seqlens_q[1:] - 1` 逐行解释**：x 进入 lm_head 时形状 `[Σq, hidden]`；`cu_seqlens_q=[0,8,9,10]` → `[1:]-1=[7,8,9]` 是每条 seq **末 query 在扁平 x 里的行号**；`x[last_indices]` → `[len(seqs), hidden]`；`F.linear` → `[len(seqs), vocab]`。decode seq 的末 query 恰好 = 它的 last_token（有用）；mid-chunk seq 的末 query 是 prompt 中间 token（无用 = 白算）。
- **`context.is_prefill` 的真实语义**：其实是"**这批走哪条 attention 路**"，不是"每条 seq 的状态"。混合批走 `prepare_prefill` → True → varlen 同时吃 q=1 与 q>1；lm_head「取每 seq 末 query」对 decode seq 也正确 → **混合批下这个 bool 本身没错**。真正缺的是：**一个批级 bool 表达不了批内 per-seq 差异**（在 varlen 这一条路内部，lm_head 不知道哪条 seq 本轮需要 logits）。
- **学生思路判定：正确**。掩码必须 (a) 在 **prepare 阶段**由 model_runner 算出（layers 拿不到 seq 对象；依赖方向 layers ↛ engine），(b) 做成**张量/数组**（他类比 cu_seqlens 是对的）。条件 = `seq.num_cached_tokens + seq.num_scheduled_tokens == len(seq)`（= 本轮算到末尾）。
- **不需要给 Sequence 加持久字段**：它是**派生量**，每步都变；且 Sequence 要 pickle 跨进程（`__getstate__`/`__setstate__`），加字段要同步改序列化。在 `prepare_*` 里现算成 tensor 塞进 context 即可。
- **关键连接（教学用）**：掩码 = `postprocess` 里 `if not is_uniform and num_cached < num_tokens: continue` 的**提前版**，两者必须一致，否则 index 错位/append 错行。且**光有掩码不够**：`zip(seqs, token_ids)` 会错位，必须改成 `zip(need_logits_slice, token_ids)` 这类显式映射。

## 追加：lm_head 白算的定位 / vLLM V1 的 logits_indices / 掩码形态
- **定位（回答"这属于混批+chunked prefill 的策略吗"）**：严格说**不属于策略本身**，是 chunked prefill **带出来的执行层优化机会**。原版 nano-vllm 的 prefill 批总是"整段 prompt"→ 每条 seq 都算到末尾 → 都需 logits → 无白算；引入 chunked prefill 后才首次出现"一条 seq 本轮只算了 prompt 的一部分"→ 其末 query 不是序列末尾 → 白算。**不做也完全正确**，纯粹省算力（P2 优化，非正确性）。
- **三层区分（教学用）**：① 策略层（scheduler：chunked prefill + 混批）；② 正确性配套（统一 varlen、per-seq 判 append，不做会算错）；③ 优化层（lm_head 白算，不做也对）。白算属第 ③ 层。
- **vLLM V1 的做法**：`InputBatch.logits_indices` —— **一维位置索引张量** `[total_num_logits]`，值是**扁平 hidden_states 的行号**（既不是 seq 下标，也不是 bool 掩码）；在 `_prepare_inputs`（GPUModelRunner）里算好，经 `forward_context` 传到层内，用法 `sample_hidden_states = hidden_states[logits_indices]` → `compute_logits(...)`。**可以为空**（全批无需采样时）→ vLLM 按 `num_logits==0` 跳过采样。参考仓库用的是 **seq 级掩码** `seq_need_compute_logits`，再 `last_indices[mask]`；两者粒度不同、语义等价。
- **注意：vLLM 的筛行发生在 model_runner，不在 lm_head**（`hidden_states[logits_indices]` 后就交给 `compute_logits`）。nano-vllm 里因 `ParallelLMHead` 自己算 `last_indices`，把多一层筛放在 lm_head 最省事，效果相同。
- **正确判据**：`seq.num_cached_tokens + seq.num_scheduled_tokens == len(seq)`（本步算到的位置 == 序列末尾）。**不是 `not seq.is_prefill`**：纯 decode 的 seq `is_prefill==False` 但**一定需要 logits**；在混合批里用 `not is_prefill` 会给出**完全相反**的答案。
- **加字段的注意点**：① 必须在 prepare 阶段算成张量塞进 context（layers 拿不到 seq）；② **不要**给 Sequence 加持久字段（派生量、每步变、要 pickle 跨进程）；③ 只在 prefill/mixed 分支需要，纯 decode 分支**不要设成空**（会一个 token 都采不出）；④ **光加字段不够**：`prepare_sample` 的 temperatures 要同样筛（参考仓库已做 `temperatures[mask]`），`postprocess` 的 `zip(seqs, token_ids)` 会错位 → 必须按数组对齐；且它与 `postprocess` 里 `if not is_uniform and num_cached<num_tokens: continue` 是同一判据的前/后两版，必须一致。
- **同一根因第三次回响**：batch 级标量表达不了批内异构 → ①调度器 bool→per-seq `is_prefill`；②lm_head bool→per-seq 掩码；③指标：batch 级时间不可归因 → per-request 延迟（TTFT/TPOT）。
- 抛给学生的问题：① `num_cached+num_scheduled==len(seq)` 与 `not seq.is_prefill` 在 {mid-chunk, decode, prefill 收尾} 三条上的结果？② 只给 1 条算 logits 时 `zip(seqs, token_ids)` 错在哪、该 zip 什么？③ 整批都不需要 logits（数组为空）时 logits/sampler 会怎样？

## 追加：warmup / graph / zip 三个实现问题（学生追问）
- **warmup 与跳行**：warmup seq 状态 = `num_cached=0, num_scheduled=seq_len(=min(max_num_batched_tokens,max_model_len)), num_tokens=seq_len` → 判据 `0+seq_len==seq_len` **为真** → 天然属于"需要 logits"，**不会被跳行逻辑误伤**，无需特判。**但别照抄参考仓库条件里的 `and seq.block_table`**（warmup 的 `block_table==[]` 会被排除 → 数组为空 → 若无条件 `x[idx]` 则 lm_head 跑 0 行，`allocate_kv_cache`(model_runner.py:108 读 `allocated_bytes.all.peak`) 会少算 lm_head 段峰值，且 warmup 不校验输出 → **静默偏移**，KV 块数估大）。
- **warmup 该不该跳过采样**：**不该**。目的：① 触发 kernel/`@torch.compile` Sampler 编译；② 给 `allocate_kv_cache` 提供峰值。sampler 只在 rank 0 被调用（`run()` 里 `if self.rank == 0`）。跳过省不了多少（warmup logits 只有 num_seqs 行），却让首次真实请求付编译开销。
- **graph 与跳行**：`capture_cudagraph` **只捕获 `self.model(...)`**（`Qwen3ForCausalLM.forward` 只返回 hidden states，见 qwen3.py:205-210），输出 `[max_bs, hidden]`；`compute_logits`/lm_head 在 `run_model` 里 **`graph.replay()` 之后 eager 调用**（model_runner.py:212）→ **lm_head 不在图内**。且会跳行的批必然含 prefill → `is_uniform==False` → **永远走 eager 分支** ⇒ 跳行对 cudagraph 无影响、无需为它捕获图。反之"把 lm_head 放进图"会固定输出形状 → **与跳行互斥**（一对互相牵制的取舍）。旁证：图外切片本就是既有手法（`graph_vars["outputs"][:bs]`）。
- **zip / 哨兵值**：根因不是 zip，而是"拿两个**长度不等**的列表 zip"（`zip(seqs, token_ids)` 会**静默错配**：need=[2]、token_ids=[t_C] → 把 t_C 配给 seqs[0]）。三方案：① **掩码+显式 zip**（推荐）：返回 `(token_ids, need_indices)`，postprocess `for idx, tid in zip(need_indices, token_ids): seqs[idx]`；② **哨兵回填**：token_ids 补回全长、跳过位 -1，zip 不变 —— 代价是把"索引对齐"换成**隐含哨兵契约**（判据漂移即静默写错 token），且 **logits 张量形状无论如何都变了**（[n_need, vocab]），哨兵只把它从张量层搬到契约层、消不掉；③ vLLM 位置索引：按请求身份（req_id↔seq）对齐，不依赖两个列表 zip。**判断标准**：跳行省的是 F.linear 的"算"，回填/映射是"搬"（便宜）→ 哨兵不违背优化目的。**最佳实践**：把 `need` 数组当**唯一真相源** —— prepare 里算一次，同时给 context（lm_head）和 postprocess 用，取代 postprocess 自己再判 `num_cached < num_tokens`，两边不可能漂移；此时 `postprocess` 的 `is_uniform` 参数也变冗余。

## 更正：「吃光预算饿死 decode」的说法是错的（学生质疑，结论：学生对）
- 学生原话：在 FCFS 下 decode 一定排在 prefill 前面。**核对 `nanovllm/engine/scheduler.py:29-59` 后确认：学生结论正确；上一轮 (b) 里"同批排在它后面的 decode seq 这一步全跑不上"是错的。**
- **定理（本仓库成立）：`self.running` 中所有 decode seq 一定排在所有 mid-chunk prefill seq 之前。** 证明要点：
  1. 「本步之后仍是 mid-chunk」⟺ `num_tokens > token_budget` → `min(num_tokens, token_budget)` 取满 → **`token_budget` 归零** → running 循环退出；且 chunked 分支不写 `is_prefill`（保持 True）。所以被调度的 mid-chunk 序列必是本步**最后一个**；它之后 running 不再推进，waiting 循环也被第 58 行早返回 + `token_budget>0` 挡住。
  2. **decode 是吸收态**：`is_prefill` 一旦被 decode 分支置 False，只有 `preempt()` 会置回 True；`num_cached_tokens` 正常路径单调增 → 不会从 decode 退回 mid-chunk。
  3. **running 顺序 = 准入顺序**（`self.running.append`）；`preempt()` 也只经 `waiting.appendleft` 后重新 append 到 running **尾部**，不会插到前面。
  → 三者合起来：不可能出现「mid-chunk 在 decode 之前」。所以 mid-chunk 吃光预算时它前面只有 decode（已各拿 1 token）。
- **真正的受害者是 waiting 里的新请求**（+ 被抢占暂居 waiting 的 seq）：`if scheduled_seqs and token_budget==0: return` 使 waiting 准入被跳过 → 长 prompt 分块期间新请求进不来 → **拖累的是新请求的 TTFT**；running 的 decode 不受影响（这正是 chunked prefill 的目的：长 prefill 不阻塞 decode）。**原文"TTFT 变好、TPOT 变差"方向说反了。**
- **更精确一层**：**正是"吃满预算"这个行为本身，造就了"decode 永远在前"的顺序**。若给单条 chunk 加上限（vLLM `long_prefill_token_threshold`，默认 `0.04×budget`），才会出现 `running=[A(mid-chunk), B(decode)]`（A 分块留余量 → B 得以准入并转 decode）；但那时 A 每步只吃上限、仍留余量给 B，所以 decode 依旧不被饿死 —— 可见"加上限"改善的是 **waiting 的公平性 / 新请求 TTFT**，不是保护 decode。
- 默认配置（`max_num_batched_tokens=16384 ≥ max_model_len=4096`）下单条 prompt 吃不完预算 → **从不出现 mid-chunk** → 该公平性问题默认不触发；只有把预算调到 < max_model_len 才可能出现。
- 待办：等待学生回答「FCFS 是不是真正的原因」（提示：FCFS 本身并不保证 decode 在前，真正保证它的是 mid-chunk 吃满预算这一行为）。

## 追加：long_prefill_token_threshold 基数更正 + 两把旋钮（学生追问 0.04）
- 查证（vLLM `vllm/config.py`、`vllm/config/scheduler.py`、官方 serve 文档）：
  - `long_prefill_token_threshold` 数据类默认 = **0**；**仅当 `max_num_partial_prefills > 1` 时**才自动设为 `int(max_model_len * 0.04)`。
  - **基数是 `max_model_len`（上下文长度），不是 `max_num_batched_tokens`。** 我上一轮写的"0.04×budget"是错的；学生据此算出的 656 也随之错。nano-vllm `max_model_len=4096` → 应为 ~164。
  - 相关默认值：`max_num_partial_prefills=1`、`max_long_partial_prefills=1`；`enable_chunked_prefill` 在 V1 默认 True；`--scheduling-policy` 默认就是 `fcfs`。
- **关键事实**：官方文档明说 `max_long_partial_prefills < max_num_partial_prefills` 会 "**allow shorter prompts to jump the queue in front of longer prompts**" → **插队能力来自 partial-prefill 并发限制，不是来自策略；默认策略恰恰是 fcfs**。直接证明"FCFS"与"decode 在前"是两回事。
- **两把独立旋钮（教学结论）**：
  1. **服务顺序**：nano-vllm = running 优先（decode 每步必拿 1 token）→ 保证 decode 不被**新来的** prefill 挡住；原版 nano-vllm = waiting 优先 + 相位分离（waiting 排到就 return）→ **prefill 步 decode 全停**；纯 FCFS = 只按到达顺序 → 长 prefill 可能挡 decode。
  2. **单条 chunk 上限**：无上限（现状 `min(remaining, budget)`）→ mid-chunk 必在 running 尾部、`[mid-chunk, decode]` 排不出、新请求被挡；有上限 → 该顺序会出现但每步留余量 → decode 仍不被饿死、新请求能进场。
- 结论：学生观察到的"decode 恒在前"主要由**旋钮 2（吃满预算）**造成；旋钮 1 只管"decode 不被新 prefill 挡"。学生问"关键差别在有没有对分块做大小限制" → **方向对了一半**（漏掉旋钮 1）。
- 另：nano-vllm 的"吃满预算"行为**等价于把并发部分预填充数强制为 1** —— 与 vLLM `max_num_partial_prefills` 默认值 1 巧合一致。

    ```python
    num_new_tokens = min(num_new_tokens, token_budget)   # v0.11 用 token_budget；main 还有 input_budget - draft_slots
    ```
    running 循环与 waiting（新请求）循环**两处都做同一夹取**（v0.11 scheduler.py:216 / 424）。
  - **`max_num_partial_prefills` 是「计数上限」**：同时允许几条请求处于 partial prefill（分块中）状态，默认 1。与 token 数无关。
  - `max_long_partial_prefills`：其中"long 请求"（prompt 长于 threshold）的并发数，设小即可让短 prompt 插队。
- **版本演化（重要，别照抄旧结论）**：
  - v0.10.2 / v0.11.0：config 里三个字段都在，`__post_init__` 里 `if max_num_partial_prefills > 1: if long_prefill_token_threshold == 0: = int(max_model_len*0.04)`。
  - 但 **V1 scheduler（v0.8.5 → main）实际并未消费 `max_num_partial_prefills`**（grep 无命中，只用 threshold 做 cap）。
  - **main 分支已删除 `max_num_partial_prefills` / `max_long_partial_prefills`**，只剩 `long_prefill_token_threshold`（默认 0=不限）+ 新增 `long_prefill_token_threshold_adaptive`。
  - main 新增两处行为：① cap 仅当 `num_eligible_reqs > 1`（running+waiting 总数）时启用，**唯一请求时让它用满预算**（注释：没有别人可饿）；② adaptive 时把 cap 下限抬到 `input_budget // num_eligible_reqs`（公平份额），避免切得比公平份额还小。
- **自动填 4% 的条件逻辑（含义）**：只有当**允许多个请求同时分块**（`max_num_partial_prefills > 1`）时，长请求才可能吃掉整个预算饿死别人 → 才需要给单条 chunk 设上限；并发=1 时任何时刻只有一条在分块，独占预算无害 → threshold 保持 0（禁用）。
- **映射到 nano-vllm**：`seq.num_scheduled_tokens = min(num_tokens - num_cached, token_budget)` 是**无 threshold** 的版本；要加 = 在 `min(budget)` 前再夹一层 `threshold`，且**只在批内请求数 > 1 时启用**（否则会白白切碎唯一的长请求）。
- 学生的理解偏差：曾把"并发数限制"与"单条 chunk 上限"当成同一件事 —— 实际是**两个独立旋钮**，一个管「几条」，一个管「每条算几个」。

## 追加：学生三点总结的判定 + main 自适应公式核实
- 学生总结：① threshold 应在请求数 > 1 时启用；② 其值应随请求数动态变化；③ 设计目的是公平性。**判定：①✓（需精确 + 是 main 新增）②半对（默认静态，仅 adaptive 才动态，且是下限保护）③✓（但有代价）。**
- main 源码细节（`vllm/v1/core/sched/scheduler.py`，已核对）：
  - `input_budget = self.scheduler_config.max_num_batched_tokens`（整批预算）。
  - `num_eligible_reqs = len(running) + len(waiting) + len(kv_holding_waiting)` —— **是所有未结束请求，不只是 running/批内**。
  - 启用条件：`threshold if num_eligible_reqs > 1 else 0`（唯一请求时让它用满预算）。**v0.11.0 无此条件**，只要 threshold≠0 就无条件夹取。
  - adaptive：`threshold = max(threshold, input_budget // num_eligible_reqs)`，注释 "Floor the cap at a fair share of the input budget so it never cuts a request below max_num_batched_tokens / num requests" → 是**下限保护**，防止 n 大时把请求切得比公平份额还碎。
  - `long_prefill_token_threshold_adaptive` 默认 **False** → 默认下 threshold 是**静态值**。
- 公平性的实质：**用长请求自身的完成速度（被切碎、多步）换其他请求的进场速度**；保护对象是 waiting 里的其他请求（不是 running 的 decode）。
- 学生决定：**不实现 threshold/adaptive**（当前模型与负载下不需要）。转向性能实验。

## 追加：实验前的代码复核（发现一个 P0）
- **P0 NameError**：`engine/model_runner.py:175` 的 `assert seq.num_cached_tokens == len(seq) - 1` 被写在 `prepare_decode` 函数体**首行**，此时 `seq` 尚未绑定（形参是 `seqs`，`for seq in seqs` 在第 181 行）→ **只要出现纯 decode 批就 NameError**。warmup 走 `prepare_prefill`（`self.run(seqs, False)`）所以没暴露；bench 第 2 步起就是纯 decode，必崩。正确位置：循环内首行，或 `assert all(s.num_cached_tokens == len(s) - 1 for s in seqs)`。**成因：学生照抄了"在 prepare_decode 开头加断言"的字面位置。**
- 已复核（推演）无问题的点：`scheduler.py:33 assert seq.block_table`（preempt 只 pop 尾部或自己，`[0, req_idx)` 不受影响，不会取到已 deallocate 的 seq）；`scheduler.py:64 assert not seq.block_table`（preempt 里 deallocate 已清空）；need_logits 的三条下游（lm_head 筛行 / temperatures 筛 / postprocess 消费序）一致；`warmup self.run(seqs, False)` 已改对；指标以 `seq.is_prefill` 为归属键（被抢占重算的 seq 归 P 桶，合理）；preempt 自 evict 判据 `req_idx == len(running)-1` 正确。
- 实验前置事实：`Config` 默认 `max_num_batched_tokens=16384`、`max_num_seqs=512`、`max_model_len=4096`。**bench 负载单条 prompt ≤1024 < 16384 → 默认配置下 chunked prefill 永不触发**；必须把 `max_num_batched_tokens` 调小（1024/2048）才能测到新代码。`bench.py` 已用 `enforce_eager=False`，注释保留了切 vLLM 的入口。
- **正确性对齐的障碍**：`sampling_params.py:11` 有 `assert temperature > 1e-10`（禁止贪心）→ 不能用 temperature=0 做逐 token 对齐；需用极小正温度（≈1e-4，softmax 减 max 后近似 one-hot）或改用合理性/统计检查。
- 预期管理：chunked prefill 对**离线端到端吞吐**未必提升（总计算量不变、forward 次数变多 → 固定开销上升），其收益主要是在线延迟（TTFT/TPOT 均衡）；正向机制是混合批同时利用算力与带宽。
