## A1 / A2 正确性验证（V1 vs main）

### 结论
- **A2（跨实现等价）PASS**：单条 seq 固定 prompt，main 与 V1 在「处理完 prompt 那次采样」的 logits **逐位相同**（max|Δlogit| = 0.000000）。budget ∈ {16384, 2048, 512} 三档全为 0，top-5 索引 5/5 一致，首 token 同为 25177。→ **V1 的 P1/P2/P3 在数值上零副作用。**
- **A1（分块不变性）数值层 PASS**：分块 vs 不分块 Δ = 0.0625 ~ 0.125，相对 absmax 3.2e-3 ~ 6.5e-3 —— 正好是 bf16 相对精度 2⁻⁸ ≈ 3.9e-3 的量级。
- **逐 token 严格一致不成立，且 main 基线自身也不满足** → 判据已修正为「数值层等价」。

### 判据为何必须改
三个机制叠加：
1. 分块改变 attention 浮点归约顺序；
2. 不同 budget 改变 batch 组成 → varlen 打包布局变化（**即使某条 seq 自身没被分块**：seq1 长度 512，在 budget=512 下整条处理，仍发生翻转）；
3. 单点翻转经自回归放大 → 整条序列不同（12 条里 6~11 条完全一致，其余被早期一次翻转污染）。

### 排除项
| 假设 | 实测 | 结论 |
| :-- | :-- | :-- |
| CUDA graph 造成差异 | `enforce_eager` 与默认结果**逐字相同** | 排除 |

### 翻转机制（gap 探针）
- gap = 采样时 top1 − top2 的 logits 间距
- 随机 prompt 首位置 gap = **0.0000**（精确平局）→ 必然翻转；同序列 gap 中位数 = 5.3
- 误差 ~0.125 ≪ gap 的位置稳定，误差 ≥ gap 的位置翻转

### 附带产出：P2（need_logits）收益量化
main 无掩码 → mid-chunk 白算 lm_head 并采样一次再丢弃。采样调用次数（prompt=3200, max_tokens=8）：
| budget | chunk 数 | main probe | V1 probe | 白算次数 |
| :-- | :-- | :-- | :-- | :-- |
| 16384 | 1 | 8 | 8 | 0 |
| 2048 | 2 | 9 | 8 | 1 |
| 512 | 7 | 14 | 8 | 6 |

白算次数 = chunk 数 − 1，完全吻合。

### 四个坑（都已踩过并解决）
1. **`dist.init_process_group` 同一进程只能初始化一次** → 每个 budget 必须起独立子进程，不能在进程内循环构造 LLM（否则 `ValueError: trying to initialize the default process group twice!`）。
2. **text prompt 池不能由仓库源码现生成** → main 与 V1 源码不同 → 池长度不同 → 随机起点不同 → prompt 完全不同，跨实现对比彻底失效（症状：A2 四个 budget 结果一模一样、都是约 10%）。修法：池缓存到 `experiments/a_text_pool.json`，跨分支共用。
3. **main 的 probe 序列比 V1 长**（无掩码 → mid-chunk 也采样）→ 直接取 `probe[0]` 会拿 prompt 中间位置的 logits 去比，得出「Δ=8.125」的**假差异**。正确对齐：`probe[len(probe) − max_tokens]`。
4. **切分支前必须 `git stash push -- .workbuddy/memory/`**，否则 tracked 文件冲突导致 checkout 失败。

## A4 抢占重入验证（V1 + main）

### 结论：PASS，未发现缺陷
| 判据 | V1 | main |
| :-- | :-- | :-- |
| L1 全部完成 / 长度正确 / 输出非空 | 24/24，**9 次抢占** | 24/24，**10 次抢占** |
| L1' 结构不变式（块覆盖 / `num_cached_tokens` 上界） | 24768 点 0 违反 | 24768 点 0 违反 |
| L2 Δ 与噪声地板之比 | 1.24× | 0.97× |
| **L3 首异位置 == 抢占点** | **0/8** | **0/9** |
跨实现（V1 抢占 vs main 抢占，同 prompt 同池）：max Δ = 5.58e-2，top1 100% 一致。

### 设计：唯一自变量 = KV 池块数
- 用 `--force-delta` 把池定为 `max(admit_need, 自然池 − delta)`。prompt / 注入方式 / budget 全同 → **prefill 批组成完全一致**，差异只在 decode。
- 高压力场景：N=24，plen=768，O∈[240,792]；强制池 72（= admit 所需），需求 132 块 → 9~10 次抢占。
- **对照不能用「逐条串行跑」**：批组成全盘不同，噪声盖过信号（实测 4 条里 1 条首 token 就翻，误报 25% Δ）。

### 关键发现 1：重入多数走「整段重算」而非「前缀命中续算」
9 次抢占重入的续算点：**7 次 `nc = 0` → 重算 768~1025 token**；只有 2 次前缀命中（512/1025、512/769）。
原因：被抢占时刚写入的块在重入时哈希链已失效（块被其他 seq 复用后 `token_ids` 被 reset，`can_allocate` 正确 break）。→ P4 覆盖的是更危险的整段重算路径。

### 关键发现 2：跨运行不存在「Δ 落在 bf16 之内」
- 同配置重跑：token 完全一致，logits **max|Δ| = 0.000000**（12384 点全 0）→ 采集管线无随机源。
- 但只把**解码批行数**从 24 改成 23，就产生 max 相对 Δlogit = **3.2e-2 ~ 5.9e-2**，是 bf16 表示精度（3.9e-3）的 **8~15 倍**。
- 所以跨运行判据只能是「与**实测**噪声地板同量级」，「落在 bf16 精度内」不可能成立（A1 的教训在换批组成时量级更大）。

### 三个新踩的坑（写进判据前提）
1. **不能按 rank 对齐比 top-5 值**：top-5 集合错位时按秩比会放大成 25% 假差异 → 必须**按 token id 求交**再比数值。
2. **缩小池必须保证 `强制池 ≥ admit 所需块数`**：否则 admit 组成变化 → prefill 批组成也变 → 抢占前 ci=0 就不一致，误报「首异位置 = 抢占点」。
3. **`torch.argmax` 与 `topk` 平局时 tie-break 不一致**（12384 点里 50 点，top1==top2 的点 98 个）→「top-1 索引相同」不是干净指标，只有 **token 序列**和**按 id 求交的 logits 差**可信。

## A1 数据补齐 + 判据澄清（回答质疑）

### 为什么报告里 A1 表只有 2 行
报告 A1 表引用的是**数值层探针**（`a_logits_probe.py`），那次命令行只传了 `--budgets 512 2048 16384`——`16384` 是不分块基准（自己跟自己比 Δ≡0，只作参照），所以剩 2 行。**不是实验只做了 2 档**：token 层（`a_correctness.py`）跑了完整 4 档。

### 数值层补齐 4 档（`results/a_logits_V1_4budget.json`，基准 budget=16384）
| budget | chunk | max\|Δlogit\| | 相对 absmax | top5 | 首 token | gap |
| :-- | --: | --: | --: | :-- | --: | --: |
| 256 | 13 | 0.125 | 6.45e-3 | 5/5 | 25177 | 2.125 |
| 512 | 7 | 0.0625 | 3.23e-3 | 5/5 | 25177 | 2.125 |
| 2048 | 2 | 0.125 | 6.45e-3 | 5/5 | 25177 | 2.125 |

注意 Δ 与 chunk 数**非单调**（7 块反而比 2 块、13 块都小）→ 进一步证明扰动来自"累加分组"而非"分块次数"。

### token 层 4 档精确结果（以 16384 为基准，逐 token）
| budget | V1 一致率 | V1 完全一致 seq | main 一致率 | main 完全一致 seq |
| :-- | --: | --: | --: | --: |
| 256 | 70.96% | 7/12 | 82.16% | 8/12 |
| 512 | 78.12% | 7/12 | 76.82% | 7/12 |
| 2048 | 70.83% | 6/12 | 65.10% | 7/12 |

两版同量级、无系统性差异；翻转位置两版重复出现（`1024@8`、`2560@21`）→ 与实现无关。

### 概念澄清（写进报告 A1 段）
- **absmax** = 该位置 logits 在 151936 个词表维度上的 |最大值|（19.375）。归一化的理由是 bf16 **相对**精度固定 2⁻⁸ ≈ 3.9e-3，绝对误差的意义取决于它相对信号量级多大。
- **gap** = top1−top2（此位置 2.125）。`gap < 误差` 才翻；随机 token prompt 首位置实测 gap=0.0000（精确平局）→ 必翻。
- **翻转放大**：翻出的新 token 成为下一步输入 → hidden state 全变 → 该 seq 之后全部位置作废。所以单个点能把一致率拉到 60~80%。
- **varlen 打包**：batch 组成变化改变各条的起止偏移 → 同一条 seq 落进不同分块边界 → 累加分组变 → 舍入变。**即使该 seq 自身长度与是否分块都没变**（这是 seq1@512 在 budget=512 下整条处理仍翻转的原因）。

### 关于「单点数值差异是否有说服力」的结论（重要）
「prefill 末位」不是随意挑的点，而是**逻辑上唯一干净的可比点**：
- mid-chunk 位置：main 白算采样、V1 被掩码跳过 → V1 没有那个输出，不可比；
- decode 位置：输入 token 依赖前一步结果，前面一翻输入就变 → logits 不同是必然，不能归因于实现；
- 只有「处理完 prompt 那一次采样」是同一输入、同一位置、两条实现路径的交点。

Δ=0 是 **bitwise 相同**，任何结构性错误（slot_mapping / positions / token-seq 错配 / 掩码错位）都会在所有位置偏移，不可能恰好此点逐位相等 → 能排除「结构性错误」这一整类。

**遗留可加强点**：`a_logits_probe.py` 其实存了**每个采样位置**的 top-5，报告只引用了 1 个。可扩展到「公共前缀内」的全部位置（翻转前的位置输入相同、logits 可比），把覆盖从 1 点提到几十点。

## C2 混合批的物理基础（H1/H2）—— 加法性成立，但窗口很窄

结论文档：`experiments/C2_混合批物理基础结论.md`。数据：`results/c2_V1b.json`、`c2_mainb.json`、`c2_shape_D{8,32}.json`、`c2_analyze_*.txt`。

### 方法（关键设计）
- **绕过调度器**，在 ModelRunner 层手工构造 batch 调 `runner.run()`。可行性来自：`run()` **不修改 seq 状态** → 可重复计时。
- 三种 batch：P-only（1 条完整 prefill）/ D-only（D 条 decode 态）/ mix（拼一个 batch）。另有 `d_gen` = decode seq 走 prefill 路径，用于分离「路径」与「token 组成」。
- 固定 `Ld=2048`；块表分区不重叠（prefill `[0,nb_p)`，decode 共享 `[nb_p, nb_p+nb_d)`）。
- **统一 `enforce_eager=True`**：默认配置下纯 decode 走 graph、混合步被迫 eager，直接比会混入 graph 加速。graph 收益留给 C3。
- 判据用 `gpu_ms_min`（CPU 抖动只让时间变长，min 最接近真实 kernel 时间）。

### 结论
| 量 | 实测 |
| :-- | :-- |
| H1 收益窗口 | **D ≤ 16**（`mix/sum` 0.54~1.00） |
| 失效临界 | **D ≈ 32**，与 P 无关（`mix/sum` 1.11~1.25）；main 也一致（13/24=54% vs V1 15/24=62%，差异是抖动） |
| D=64 的代价 | `a_est = t_p+t_d−t_mix` = **−27 ~ −53 ms**（混批比分开两步还慢 20~38%） |
| 单条 decode 的相对成本 | **P 越大越便宜**：P=512 +15%、P=2048 +9%、P=4096 **+6%** |
| 纯 decode 的边际 | **0.08 ms/条**（D 1→32 只慢 17%）→ 已被固定开销支配 |
| 两版一致性 | P=4096,D=8：V1 242.9 / main 244.3 ms → **执行层属性，与调度无关** |

### 根因（C2b 两个旋钮定位）
| 旋钮 | 操作 | 结果 |
| :-- | :-- | :-- |
| 1 拆 P | P 拆成 k 条（`max_seqlen_q` 2048→128） | `t_mix` −16%，但 **`t_p` 同步 −16%**，`mix/sum` 几乎不变 → **排除形状假设** |
| 2 去历史 | decode 长度 2048→1（`cu_seqlens_k == cu_seqlens_q`，不准备 `block_tables`） | D=32 时 `t_mix` **141.7 → 97.3 ms**（t_p=93.9）→ **32 条 decode 只花 3.4 ms** |

**根因：混合批被迫用 `flash_attn_varlen_func(q, k_cache, v_cache, block_table=…)` 读 paged KV；纯 decode 用专用的 `flash_attn_with_kvcache`。**
- 混合批内 32 条 decode 的成本 = 47.8ms = **linear 3.4ms + attention 读 paged KV 44.4ms**
- 同样 32 条走专用 kernel = 26.4ms
- 也解释了 `t_d` 在 D=64 的台阶（27→45ms）：那是专用 kernel 从"固定开销支配"转入"KV 带宽支配"的拐点，与混合批无关。

### 表述陷阱（写文档时必须注意）
"混批内 decode 边际 / 纯 decode 边际 = 14~16×" **有误导性** —— 分母接近 0 把比值放大。更稳的口径是**总量比**：D=32 时混合批里 decode 花 45.4ms vs 单独跑 26.4ms = **1.7×**。

### 对 B 组的含义
- B2 设计的 resident ≈ 12 落在收益窗口（D=8~16，`mix/sum` 0.93~0.99），**但余量很小**。
- **「混合调度提升利用率」有适用边界**，不能无条件陈述：resident 过大时混合步反而拖慢整步。

### ⚠️ 重大坑：`run()` 第二参数语义两版相反 —— 导致一整轮数据作废
| 分支 | 签名 | `True` | `False` |
| :-- | :-- | :-- | :-- |
| V1 | `run(seqs, is_uniform)` | decode | prefill |
| main | `run(seqs, is_prefill)` | **prefill** | **decode** |

第一轮对两版都传 `False`：V1 对，**main 的「P-only」实际跑的是 `prepare_decode`**（只处理 1 token）。症状：`t_p` 恒定 22ms、与 P（512→4096）完全无关 —— 而 prefill 的 attention 是 O(L²)，不可能平。
**修法**：`inspect.signature(runner.run).parameters[1]` 取参数名自动映射；并加自检 `t_p(4096)/t_p(512) > 1.5`（实测 7.79 / 8.08）。
**注意**：main 的 `prepare_decode` **没有** `num_cached_tokens == len−1` 断言 → 传错不崩，只静默给错数据；V1 有断言反而安全。

### 其它坑
- P=512 时 `t_p` 单次抖动可达 41%（26.4~37.8ms）→ 分析时加「同 P 跨 D 中位数」降噪（`mix_over_sum_robust`）。
- decode seq 必须先真实 prefill 一次填 KV，避免 attention 读到未初始化显存。
- 两版 `run` 返回值不同（main 返回 `token_ids`，V1 返回 `(token_ids, need_logits)`）—— 本实验忽略返回值即可。
