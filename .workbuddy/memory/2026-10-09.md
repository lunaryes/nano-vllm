## Review：scheduler.schedule() 的 V1 混合调度改动（学生提交，未通过）
按类型归类：
**思路错误**
1. 第二个返回值 `is_prefill` 语义被换成 `token_budget == 0`，但它在 `LLMEngine.step` / `ModelRunner.run` 里决定走 `prepare_prefill` 还是 `prepare_decode` 两条互斥路径；预算用尽与"批的性质"无因果关系。混合批用单一 bool 无法表达（现有 runner 也不支持）。
2. decode/prefill 判别式 `num_cached_tokens >= num_tokens` 恒为假 → decode 分支死代码。正确不变式：`num_cached_tokens = num_tokens - 1`；应按 `num_cached_tokens >= num_prompt_tokens`（或 `num_tokens - num_cached_tokens <= 1`）判别。
3. 用 `req_idx` 下标遍历 `self.running`，循环内又 `self.running.pop()` —— 边读边改同一容器。
**细节错误**
4. `waiting.popleft()` 先弹再判 `can_allocate() == -1` → 失败丢请求（原版用 peek `waiting[0]`）。
5. decode 分支 `scheduled_seqs.append(seq)` 重复（分支内 + 第 54 行无条件）。
6. running 循环无 `req_idx < len(self.running)` 保护 → IndexError（running 非空时第二圈必崩）。
7. `preempt(seq); break` 后该 seq 仍被减预算并 append 进 scheduled。
8. chunked prefill 分支未设 `is_prefill`、未做跨块 `may_append` 分配。
教学方式：按项目约定只给分类 + 引导性问题，未给完整实现。

### 学生追问后的结论（补充）
- 学生已修：4/5/6（waiting 改回 peek `waiting[0]`；加 `req_idx < len(self.running)`；删内层重复 append）。
- 判别式：学生提出 `num_cached_tokens >= num_tokens - 1`。能修"恒为假"，但**边界错**：chunked prefill 只剩最后 1 个 prompt token 时会走 decode → 触发 `may_append`，而该块在 waiting 已 `allocate`（覆盖整个 prompt），`may_append` 会**多分一块** → `block_table[-1]` 指向新空块，`prepare_decode` 的 slot 算错、KV 写错位置。正确边界应比 `num_prompt_tokens`：`num_cached_tokens >= num_prompt_tokens`（即 vLLM 的 prefill/decode 判定）。
- 8 学生判断正确：prefill 块在 waiting 已分配完，prefill 分支不需要 `may_append`，`is_prefill` 默认 True 也对。此判断恰好印证上面边界坑。
- index+pop 的真实危害（比越界更重）：单序列 running 且 free=0、`len(seq)%bs==1` 时，`self.running.pop()` 弹出的正是当前 seq → 它已被 `preempt` 进 waiting；dealloc 后 free 变多 → `can_append` 转真 → while 正常结束 → `else` 把一个已 deallocate、已在 waiting 的 seq 当本轮候选提交 → 同一 seq 同时在 waiting 和 scheduled_seqs。（学生加的 guard 挡越界但挡不住这个。）
- 7 的解决思路：只有真正排进本轮的 seq 才做"设 num_scheduled_tokens / 扣预算 / append"三件事；被 preempt（含 preempt 自己）不 commit。原 decode 循环的 `while ... else`（else 仅在 can_append 转真时执行，break 不执行）就是"提交绑成功"的现成模板。

### 学生追问：单 running 序列且无空间 = "完全跑不了"？
- 澄清三点：
  1. `can_append` 为假 ⟺ `len(seq)%block_size==1` 且 `free_block_ids==0`。free==0 表示所有块都被 running 序列占满；若 running 只有 1 个序列，意味着该序列占据**整个 KV 池**。正常配置下（一个序列长度 ≤ max_model_len，池容量 ≫ max_model_len/block_size）不可能发生。
  2. 即便人为把块数调小来触发：`preempt()` 用 `waiting.appendleft` 把 seq 放到 waiting **队首**，同一次 `schedule()` 的 waiting 阶段会重新 `can_allocate`（刚刚释放的块 + 前缀缓存复用）→ 重新调度，引擎继续推进，**不会卡死**。
  3. 真正会"跑不了"的只有一种：序列长度 > 整个 KV 池容量（配置/长度问题），此时 `can_allocate` 永远 -1 → `assert scheduled_seqs` 触发（是合理报错，不是调度器能修的）。
- 结论：preempt-self 分支是**防卡死**的正确设计，问题只在于 preempt 之后还 commit 了它（bug 7）。保留 preempt-self、去掉 commit、保证流程能走到 waiting 阶段即可。

### 第三版 review
- 已修对：① `seq.num_cached_tokens >= seq.num_prompt_tokens`（decode 判定边界）；② 采用 `while not can_append: ... else: <commit>`，把 commit 绑在"成功"上（victim 路径正确）；③ waiting 用 peek `waiting[0]`。
- **新引入 bug（preempt 分支）**：
  ```
  while not can_append(seq):
      if len(self.running)==1:  self.preempt(seq)      # ← 错
      else:                      self.preempt(self.running.pop()); break
  else: <commit>
  ```
  `preempt(seq)` 只做 `waiting.appendleft` + `deallocate`，**不会**把 seq 从 `self.running` 移除。于是：seq 仍在 running → while 重新判断 `can_append(seq)`（刚 deallocate、free 变多）→ 变真 → 走到 `else` → 把已 preempt、已在 waiting 的 seq commit 进 scheduled_seqs。结果 seq 同时在 running + waiting + scheduled 三处；随后 line 65 `assert not seq.block_table`（block_table 被 may_append 加了块）会 AssertionError。
- 修法：`len(self.running)==1` 时 `self.running.pop()` 弹出的**就是 seq 本身**，所以这个 `if` 分支完全多余——删掉它、只留 `else: self.preempt(self.running.pop()); break` 即可，单序列情况自然正确（break 跳过 commit，running 空 → 落到 waiting 阶段重调度）。
- 仍挂起：返回的 `is_prefill` 仍由 `token_budget==0` 决定（学生自称 TODO，但仍会生效）。

### 第四版 review
- 改动：`if len==1: preempt(seq); break`（补了 break）；`else: preempt(pop())` 去掉了 break（改为在 inner while 里继续逐个 evict victim）——后者是对的。
- **根问题仍在**：`preempt(seq)` 不移除 running 成员。
  - (A) `len==1` 分支：preempt(seq) 后 seq 仍在 running（block_table 已清空、status=WAITING、又进了 waiting）。break 跳过 commit 后，外层 while 再取 `self.running[0]`（还是 seq）→ line 33 `assert seq.block_table` **AssertionError**。
  - (B) "有没有 victim"的判据用 `len==1` **不对**：当 `req_idx == len-1`（正在处理队尾）且 len>1 时，`self.running.pop()` 弹出的就是 seq 自己；走 else、无 break → while 重新判断 can_append（dealloc 后为真）→ 正常结束 → 又 commit 了已 preempt 的 seq。
  - 正确判据："我要 pop 的那个元素是不是 seq 本人"（`victim = pop(); if victim is seq: break`），它同时覆盖 len==1 和 req_idx==tail 两种情况。根因是 seq 在 evict 期间仍留在 running 里。
- 引导方式：问 (A) 下一圈 outer 的 assert；(B) req_idx==tail 时 pop 弹出谁。

### 第五版 review（running/preempt 逻辑判定为正确）
```
while not can_append(seq):
    if req_idx == len(self.running)-1:   # 等价于"pop 出来的就是 seq 本人"
        self.running.pop()               # 真正把 seq 移出 running
        self.preempt(seq)
        break                            # 跳过 commit
    else:
        self.preempt(self.running.pop()) # evict victim（队尾、req_idx 之后），继续循环
```
- 等价性成立的原因：`seq == running[req_idx]`，`pop()` 移除 `running[-1]`，二者相同 ⟺ `req_idx == len-1`；且全程只从队尾 pop、不移 req_idx 之前的元素，`running[req_idx]` 恒为 seq。
- 该分支同时满足"移出 running"+"跳过 commit"两个必要条件 → running 循环逻辑通过。
- **剩余问题：返回的 `is_prefill`**。当前 `token_budget==0 ? True : False` 与批语义无关：running 里未填满预算的 chunked-prefill seq（budget>0）会返回 False → engine 调 `prepare_decode`（假设每 seq 1 token、positions=len-1），但该 seq 的 `num_scheduled_tokens` 是多个 token → 不匹配。混合批用单一 bool 无法表达。下一步引导方向：批性质应看"批里有没有 prefill 工作"，并决定是(禁混合：每步全 prefill 或全 decode)还是(改 model_runner 支持混合)。

### 关键设计讨论：混合批的 attention 怎么走（学生的"按 seq 标签分流"思路）
- 学生想法：batch 里既有 prefill 又有 decode 时，按 seq 的标签分组，各自进 prepare_prefill / prepare_decode。
- **卡点**：`layers/attention.py` 第 64 行 `if context.is_prefill:` 用的是 `Context.is_prefill` —— 这是**整批一个全局 bool**（`utils/context.py`），attention 层**拿不到 per-seq 标签**。所以"在一次 forward 内部按 seq 分流"做不到；退而求其次只能分两次 forward（各设一次 context），但那等于跑了两次模型（linear/MLP 也跑两遍），不是真正的混合。
- **V1 的统一做法**：`prepare_prefill` 走的 `flash_attn_varlen_func` 是**变长**的，`cu_seqlens_q` 表达"每条序列本轮算几个 query"。decode 就是 `num_scheduled_tokens==1` 的特例：`start=num_cached`、`end=num_cached+1`、positions=[len-1]、input_ids=[last_token]、单条 slot_mapping —— 与 prepare_decode 对一条 decode seq 做的事一致（causal 采用右下对齐，q_len=1 时 attends 全部 key）。所以**不必拆**：把 decode 也塞进 varlen 路径即可（有 decode 就有前缀，`prepare_prefill` 的 `if cu_seqlens_k[-1] > cu_seqlens_q[-1]: block_tables=...` 天然成立）。
- 代价：统一后 decode 用不了 `flash_attn_with_kvcache` 的 paged kernel + cudagraph（形状不固定）。
- 记忆要点：这条是"混合调度能否落地"的分水岭，学生在两条路（两次 forward vs 统一 varlen）之间做选择。

### 学生反驳"放弃 cudagraph 很亏"——查证 vLLM V1 的真实做法
- 学生是对的：V1 大量使用 CUDA graph，而且不是二选一，而是**按批动态 dispatch**。
- vLLM V1 官方概念（docs/design/cuda_graphs.md）：
  - 术语：`uniform decode batch` = max_query_len==1（纯 decode / 投机解码）；其余为 `non-uniform`（prefill 或 mixed prefill-decode）。
  - `CUDAGraphMode`：NONE / PIECEWISE（attention 保持 eager，其余入图，最兼容）/ FULL（仅对 non-uniform 捕获全图，uniform decode 复用同 batch_size 的图）/ FULL_DECODE_ONLY（只对 uniform decode 全图）/ **FULL_AND_PIECEWISE（默认）= uniform decode 全图 + prefill/mixed 用 piecewise**。
  - 有 **CUDA Graphs dispatcher**：运行时按 batch 组成自动选具体模式。
  - 部分 attention backend（FlashInfer/MLA/Mamba 等）**只支持 pure decode 批**上 graph。
- 结论（回答学生）：cudagraph 的硬约束是**形状静态** → uniform decode 形状固定可全图；prefill/mixed 形状不定 → 不上全图（可用 piecewise）。
- nanovllm 的落地建议（在项目约束下）：`run_model` 目前凭 `not is_prefill and not enforce_eager and bs<=512` 上 graph。可改为**按批构成分流**：纯 decode（所有 seq 的 num_scheduled_tokens==1，即 max_query_len==1）→ 保留 paged decode kernel + full graph；否则 → 统一 varlen（attention eager）。即"统一 varlen"与"保留 decode graph"**共存**，不是二选一。
- 注意：scheduler 一旦开始混合，纯 decode 批会变少 → graph 触发频率下降，是真实代价（V1 用 piecewise 缓解；nanovllm 若不做 piecewise 则接受该代价）。

### 参考实现核查：anjoj0/nano-vllm-v1（学生问"它是不是也这么做"）
- 已 clone 到临时目录并逐文件读完（scheduler / model_runner / attention / llm_engine / block_manager / context / sequence / config / example / bench / serving_bench）。
- **核心结论：它与上一轮建议的"两条路按批分发"不同——它把两条路彻底合并成一条，且比建议更激进。**
- 具体做法：
  1. `schedule()` **删掉了第二个返回值**（`return scheduled_seqs`，但签名注解 `-> tuple[list[Sequence], bool]` 未改干净）。engine 不再接 is_prefill。→ 学生纠结的"is_prefill 由什么决定"在它这里被"取消问题"解决。
  2. **没有 prepare_prefill / prepare_decode**，只有一个 `prepare_model_input`：每条 seq 统一按 `seqlen_q = seq.num_new_tokens`、`seqlen_k = seq.num_context_tokens` 描述。decode 就是 `seqlen_q==1` 的特例——把上轮"decode=q_len 1 的 prefill"落实成代码。
  3. `block_tables` 仅在 `cu_seqlens_k[-1] > cu_seqlens_q[-1]`（有前缀缓存或 decode）时构造。
  4. `attention.forward` **无条件走 `flash_attn_varlen_func(..., block_table=context.block_tables)`**，连 `flash_attn_with_kvcache` 都不再使用（第 6 行仍 import）。→ 混合批 = 一次 varlen 调用。
  5. "哪些 seq 要算 logits/采样"用一个 **per-seq 掩码 `seq_need_compute_logits`**（`len(seq) == num_cached + num_new` 时才算）取代了全局 is_prefill——这是它替代"第二个返回值"的关键设计。
  6. scheduler 先 running（可 chunk）再 waiting；waiting 段有 `if not preempted_seqs` 守卫（有抢占就不收新请求）。
- **CUDA graph 与 V1 官方不同**：`run_model` 判据是 `enforce_eager or input_ids.size(0) > 512`（批内总 token 数），不是"批构成/uniform decode"dispatcher。
- **疑点（留给学生验证）**：`capture_cudagraph` 里 `set_context` 只设 slot_mapping/context_lens/block_tables，**未设 cu_seqlens_q/k**，而 attention 现在无条件读 cu_seqlens → graph 路径与统一 varlen 存在张力。且 example.py / serving_bench.py 都写死 `enforce_eager=True`，仅 bench.py 用 False。

### 学生四问答复要点（掩码 / graph / 优缺点）
- **为什么需要掩码，bool 不行吗**：bool 方案**可行**（把 is_prefill 定义为"批里有任何 seq 没 prefill 完"），学生 `postprocess` 里 `if is_prefill and seq.num_cached_tokens < seq.num_tokens: continue` 本身已是 per-seq 判断，错的只是 is_prefill 的**判据**（`token_budget==0`，第 58 行）。掩码买的是三件事：
  1. **省 lm_head**：v1 只对"这一步真的产出 token"的 seq 算 vocab 投影；学生的 `ParallelLMHead` 对 prefill 每 seq 都取 `cu_seqlens_q[1:]-1`，会给 mid-chunk 序列也算（浪费）。
  2. **index 对齐**：只给部分 seq 算 logits 后 `len(token_ids) != len(seqs)`，`zip` 会错位 → 必须显式 index 映射（v1 postprocess 用 `zip(seq_need_compute_logits, token_ids)`）。
  3. **去掉全局标志依赖**：postprocess / lm_head 不再读 is_prefill，混合批天然正确。
- **graph**：v1 **写了** capture + replay（不是没用）。但它把 decode 从 `flash_attn_with_kvcache` 换成 varlen 后，attention 需要 `cu_seqlens` —— 而 `graph_vars` 里**没有** cu_seqlens、capture 时也没 set → 这条路很可能 capture 阶段就失败。
- **关键对照：学生仓库（原始 nano-vllm）的 graph 是对的**——`is_prefill=False` 走 `flash_attn_with_kvcache(q, k_cache, v_cache, cache_seqlens=context_lens, block_table=...)`，其三个输入 slot_mapping / context_lens / block_tables **全在 graph_vars 里**，可每步更新后 replay。
- **结论（改造目标）**：不是"统一 varlen 一条路"，而是**两条路共存 + 按批分发**：纯 decode 批（所有 seq `num_scheduled_tokens == 1`，即 max_query_len==1）→ `with_kvcache` + full CUDA graph；含 prefill / 混合的批 → 统一 varlen（attention eager）。V1 用 piecewise 让混合批也图住非 attention 部分，nano-vllm 量级可先不做。
- **v1 优缺点**：优 = 掩码让混合批天然正确、省 lm_head、单条 attention 路径代码短、eager 下永远正确；缺 = 丢掉 decode 专用 paged kernel 及与之配套的 cudagraph、graph 判据（批内总 token 数 >512）不是"批构成"判断、无 piecewise → 混合批只能 eager。
- 追加确认（读学生仓库源码）：`nanovllm/utils/context.py` 的 Context 带 `is_prefill`；`layers/embed_head.py::ParallelLMHead.forward` 里 `if context.is_prefill: last_indices = cu_seqlens_q[1:] - 1`。

### 学生追问："前向计算中怎么区分 prefill/decode 决定要不要把输出加到 seq"
- 要点一：**模型 forward 本身完全不区分**。整条链路只有 3 处用到，且**粒度不同**：
  - `prepare_*`（engine 层，能看 seq 对象）→ 需要 **per-seq**：起点 / 这一步算几个 token；
  - `attention`、`ParallelLMHead`（layers 层，只能看 context 张量）→ 只有一个 **整批 bool** `context.is_prefill`；
  - `postprocess`（engine 层，能看 seq 对象）→ 需要 **per-seq**。
- 要点二（关键纠正）：**"要不要 append" 的判据不是"prefill 还是 decode"，而是"这条序列这一步有没有算到它的末尾"**。学生 `postprocess` 里 `if is_prefill and seq.num_cached_tokens < seq.num_tokens: continue` 中，`is_prefill and` 其实是**多余**的——纯 decode 时 `num_cached` 加完正好 == `num_tokens`，条件不会触发。所以那个判断本身就已经是 per-seq 的。
- 要点三（架构约束，解释掩码为什么必须是张量）：layers 层拿不到 `seq` 对象，只能读 `context` 里的张量；所以任何"per-seq 决策"要跨到 layers，就必须由 model_runner 先算成**张量**塞进 context —— 这就是 `seq_need_compute_logits` 存在的结构性原因。

### 学生追问：能否去掉返回值 bool、纯 decode 走 graph 其他走 eager
- 学生方案：`schedule()` 不再返回第二个 bool；纯 decode 批 → `flash_attn_with_kvcache` + cudagraph，其他批 → `prepare_prefill`（统一 varlen，eager）。当前仓库状态未变（`scheduler.py:25` 签名仍 `-> tuple[list[Sequence], bool]`，第 58 行仍 `token_budget==0 ? True`）。
- 判定：**可行，且分工更干净**（scheduler 不再做执行层决策）。但"去掉 bool"≠不判断——决策点从 scheduler 搬到 engine 层（`ModelRunner.run`，唯一同时握有 seqs 且调用 `prepare_*`/`run_model` 的地方；layers 层拿不到 seq，scheduler 不该知道 kernel/graph）。
- **关键判据（本轮以问题引导，未给实现）**：
  - graph 路前提 = 形状静态 ⟹ 每条 seq 本轮恰好 1 token；
  - `prepare_decode` 前提更严：写死 `input_ids=seq.last_token`(=token_ids[-1])、`positions=len(seq)-1` ⟹ **每条 seq 本轮算的那 1 个 token 必须是它的 last_token**（即 `num_cached_tokens == num_tokens-1`）。
  - **陷阱**：只写 `all(num_scheduled_tokens == 1)` 不够——chunked prefill 被预算卡成 q_len==1 时形状像 decode，但 `prepare_decode` 会取 `token_ids[-1]`（prompt 末 token），而正确输入是 index=num_cached 的 token → **取错 input token**。这与第一版 `token_budget==0` 属同类错误：用与真实前提不等价的近似量。
  - 可站住的写法：① `all(not seq.is_prefill)`（安全、略保守，prefill 收尾 q_len==1 时少上一次 graph）；② `all(seq.num_cached_tokens == seq.num_tokens-1)`（直接表达 last_token 前提）。
- 混合批仍存在，走 `prepare_prefill` 时 decode seq 靠 q_len==1 天然走通；`postprocess` 去掉 bool 后按 per-seq `num_cached < num_tokens` 判断即可（decode→append / mid-chunk→skip / 收尾→append）。
- 代价（前几轮已记）：混合调度使纯 decode 批变少 → cudagraph 触发率下降；V1 用 piecewise 缓解，nano-vllm 量级可先接受。

### 讨论：对照 vLLM，学生方案要不要改进 / 要不要上 piecewise
- **定位**：学生的方案（纯 decode 走 full cudagraph，其余 eager）在 vLLM 里对应正式模式 **`FULL_DECODE_ONLY`**（uniform decode 全图、prefill/mixed 不上图），官方用于 P/D 分离的 decode 实例。→ 是被支持的"一档"，不是权宜之计。
- **两层要分开**：
  - **调度层**：学生已与 vLLM 同构——每序列用 `seq.num_scheduled_tokens` 描述本步工作量，等价于 vLLM 的 `num_scheduled_tokens: dict[str,int]`；只是额外回传一个整批 bool 给执行层。vLLM 用 dict 是为增量传输（new/cached reqs）、DP、KV connector 服务，**单进程单卡不需要，别照抄**。
  - **执行层**：vLLM 有 piecewise 编译 + `CudagraphDispatcher` + `BatchDescriptor`；nano-vllm 无此基础设施（手写 attention 的普通 nn.Module，`capture_cudagraph` 直接捕获 `self.model(...)`）。
- **piecewise 现在不值得做**：前置是 piecewise 编译（按算子切 FX 图、把 attention 抠出）；工程量 ≫ 收益，且收益只在"混合批占比高"时出现。**且 piecewise 不解决"混合批 attention 怎么算"**——它解决的是"非 attention 部分能不能图住"，attention 仍须统一 varlen 或两次 forward。两件事正交。
- **更便宜的退路（若想保 graph 命中率且不上 piecewise）**：调度层**不混合**（每步要么全 prefill 要么全 decode，即原版 nanovllm 的"waiting 优先，排到就 return True"）。代价：prefill 阻塞 decode 延迟。→ 本质是"混合调度收益 / graph 命中率 / 实现复杂度"三选二。
- **现在值得做的（性价比序）**：① 先写对 `is_prefill = any(seq.is_prefill)`（前提）；② 混合批 lm_head 浪费 → per-seq 掩码（可选）；③ scheduler 的 `if not preempted_seqs` 守卫（参考仓库有，可选）；④ **先测量** graph 命中率与批构成，再谈 piecewise。
- 别照抄的：`num_scheduled_tokens` dict、`BatchDescriptor`、dispatcher——为多后端/多进程/投机解码准备，nano-vllm 量级用不到。

### 讨论：prepare_prefill 与 prepare_decode 高度一致吗？要不要融合？
- **结论：decode 就是 prefill 在 `seqlen_q == 1` 时的特例**。把一条 decode 序列代进 `prepare_prefill` 的式子（start=num_cached=len-1、q=1、end=len）：`input_ids` / `positions` / `slot_mapping` 三项产出**逐个相等**于 `prepare_decode`（已按 block 边界验算：num_tokens%bs==0 与非 0 两种情形均吻合）。
- **分不开的是后 5 项**：① 长度元数据（varlen 要 `cu_seqlens_q/k`+`max_seqlen`；decode 要 `context_lens`）；② 块写槽逻辑（prefill 可跨多块、按区间展开；decode 每 seq 单槽）；③ `block_tables` 必要性（prefill 仅前缀缓存 Σk>Σq 时；decode 总是）；④ `lm_head` 取值（prefill 取 `cu_seqlens_q[1:]-1` 即每 seq 末 query；decode 全量）；⑤ **形状/图**（decode 总 token 数=序列数→固定→可 cudagraph；prefill 变长→不能）——这是最实际的理由。
- **"要不要区分 prepare" 的正解**：要区分，但区分的本质是**选 attention 路径**，prepare 只是替它备元数据；**不可能只在 prepare 层融合而保留两条 attention 路**（两条路元数据不同，融合后内部仍要分）。真正"融合成一个 prepare"只在 **attention 也统一成一条 varlen 路**时才成立（v1/参考仓库做法），代价是丢 `flash_attn_with_kvcache` + cudagraph。
- **推荐切法**：混合批 → 复用 `prepare_prefill`；纯 decode 批 → `prepare_decode`。三条理由：① 混合批里 decode seq 的 q=1 自动走通；② `if cu_seqlens_k[-1] > cu_seqlens_q[-1]` 在有 decode seq 时**必为真**（其 k 比 q 长）→ `block_tables` 自动备好；③ 纯 decode 批仍走 `prepare_decode` → 保住 with_kvcache + graph。
- 反问引导：让**纯 decode 批也走 `prepare_prefill`** 会怎样？→ 不会算错，但白丢 with_kvcache 与 cudagraph（q=1 的 varlen 能算，但不如 paged kernel 快、且上不了图）——正是 v1 仓库付出的代价。
- 另注：decode seq 的块 append（`may_append`）在 scheduler decode 分支完成，与它最终落在哪条 prepare 路无关，故混合批里 decode seq 的 `block_table` 已含所需块。

### 讨论：混批下怎么算吞吐量
- **原记法的本质**：`num_tokens = +Σnum_scheduled_tokens（prefill）/ -len(seqs)（decode）`，用**正负号给"整个 step"打标签**。它成立的前提是原版 nano-vllm **相位分离**（一步要么全 prefill 要么全 decode）——符号法只是相位纯净的**副产品**，不是设计目标。混批后一步内含两种 work → **符号法无定义**。（且 `sum(num_scheduled_tokens)` 在纯 decode 下恰好 == len(seqs)，符号法好用的第二重依赖也成立。）
- **为什么原来要分两个数**：prefill 与 decode 是两种 regime，瓶颈不同——prefill 计算密集（大 matmul）、tok/s 千～万级、对应 **TTFT**；decode 带宽密集（反复读 KV cache）、tok/s 十～百级、对应 **TPOT**。两者差一个数量级，混成一个数 → 看不出瓶颈在算力还是显存带宽。每个数各自独立。
- **同一根因回响**：`is_prefill` bool → per-seq 的教训在**指标层**再出现一次：**批级标量表达不了批内异构**。解法同样是"下移到 per-seq 计数"。
- **三种替代记法**：
  1. **单一总量**（参考仓库 v1 的选择）：`num = Σ num_scheduled_tokens`，永远正确、无歧义，但语义随批构成漂移（分不清 regime）。v1 实际写的是 `sum(len(seq) for seq in seqs if seq.is_finished)` + 累计 / 总时长（工作负载级 co-arse 指标）。
  2. **按 seq 归属分两个计数**（vLLM 做法）：`prefill = Σ num_scheduled_tokens for seq if 仍在 prompt`；`decode = Σ for seq if 已进入 decode`（每条 1）。用两个累计计数器 → 两个吞吐。归属键：`seq.is_prefill` 是现成近似，**更严谨的是 `seq.num_cached_tokens < seq.num_prompt_tokens`**（is_prefill 在 prompt 收尾那步仍为 True，恰好把该步的 prompt token 正确归为 prefill）。一条 seq 在同一步不会同时落两桶。
  3. **每请求指标**：用 TTFT / TPOT 取代批吞吐，批混合时延迟才是真实体验。
- **另一层要分清**：原代码是**瞬时吞吐**（每步 `num/step_time`，只更新其中一个数，另一数保留旧值）→ 抖；混批下更抖。建议改**累计**（`total_tokens += num; throughput = total / elapsed`）。
- 已知的两处待修（上条已记）仍在：`llm_engine.py:52` 符号反转；`generate()` 里 `if num_tokens > 0` 的分支依赖旧符号语义。
- 引导问题（本轮抛出，未答）：① 归属键用 `seq.is_prefill` 还是 `num_cached < num_prompt_tokens`？② 同一步里一条 seq 会不会同时给两个桶贡献 token？③ 做 chunked prefill 调参时你真正关心哪个数？
