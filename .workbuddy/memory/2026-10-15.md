## 判定：方案部分可行（先查清、再动手）
| 项 | 判定 | 依据 |
| :--- | :--- | :--- |
| 应用层全部 8 项 | ✅ 可测 | `scheduler.running/waiting`、`block_manager.used_block_ids` 可直接逐步采样 |
| GPU / 显存控制器利用率 | ⚠️ 粗粒度 | 只有 nvidia-smi（无 ncu/nvtop/dcgmi）；`-lms 500` 流式可用，单次 69 ms |

## 双口径设计（用户选：双口径 + 压测兼机制归因）
- **stress（真实压力）**：官方 bench.py 口径（N=256、P~U[100,1024]、O~U[100,1024]、budget 16384、ml 4096、不 patch 采样）→ 抢占 166/172、waiting 均值 82.8 条
- **ctrl（受控）**：定长 1024（O~U[64,255]、P=总长−O，块数恒 4）→ 并发 ~36、**抢占 = 0**
  - 锁抢占的**代码级依据**：`Scheduler.schedule()` 只在 decode 分支 `can_append` 失败时 `preempt()`；
    块数恒定 → `can_append` 恒真 → 永不抢占。实测两版 prefill/decode token **逐位相同**（221442/221437、40454/40453）

## 核心结果
1. **stress：两版持平** V1÷main 墙钟 1.010（交替配对 4 对：1.013/1.020/1.001/1.007），输出 TPS 0.990。
2. **ctrl（抢占 0）：V1 慢 4.4%**（36.80 vs 35.27 s），工作量逐位相同 → 差异纯来自调度形态。
   机制 = 并发 36 越过 C2 的混合步收益窗口（D ≤ 16）。
3. **ITL p99 与 p999 交叉**：stress 下 main÷V1 在 p99 = 0.950（main 好 5%）、p999 = **1.192**（V1 好 19%）。
   → 只报 p99 会得出"V1 更差"，只报 max 会得出"V1 大胜"。
4. **步延迟 P999：V1 118.2 vs main 85.8 ms（+37.8%）** —— 与参考数据 −36.1% 幅值几乎相同、**符号相反**。
5. **峰值显存：6186.5 vs 6186.3 MB（−0.003%）** —— 参考的 −3.0% 不存在。
6. 硬件层无差异：GPU 95.9/95.2%、显存控制器 96.3/96.5%；KV 峰值两版都 1.00（池是唯一瓶颈）。

## 决定性证据（C5 budget 扫描，ctrl + 定长 4864 + 池 163 + n=32）

| ---: | ---: | ---: | ---: | ---: |
| 1024 | 102.3 | 71.6 | 5766.2 | 5766.2 |
| 2048 | 161.8 | 143.1 | 5794.3 | 5794.3 |
| 4096 | 276.9 | 215.9 | 5850.3 | 5850.3 |

- **步 P999 的主因是 budget**：16384→1024，两版都降约 **90%**（main 744.6→71.6）。
  这就是参考数据「−36.1%」的同一根杠杆，只是 nano-vllm 里拧它的是 `max_num_batched_tokens` 而非调度。
- **峰值显存的主因也是 budget**：16384→1024，main 省 6.3%、V1 省 7.3%（与 −3.0% 同量级同方向）。
- **同 budget 下两版峰值逐位相同（+0.00%）** → **显存是配置效应，不是调度效应**。16384 档 V1 反而高 0.94%。

# 追加 · 与 vLLM 官方口径对照（回答「我们的结果和 vLLM V1 的收益吻合吗」）

## 官方口径的三份主张（必须分开，这是回答问题的全部关键）
1. **vLLM V1 alpha 博客（2025-01-27）**：「up to **1.7x** higher throughput compared to V0」，
   归因原文：**「These dramatic performance gains stem from comprehensive CPU overhead reductions
   across the entire stack」**；并说「the kernels used for V0 and V1 are almost identical, the performance
   difference is mainly due to the architectural improvements (**reduced CPU overheads**)」。
   → **1.7× 是执行循环重建（EngineCore 多进程 / 持久输入 / torch.compile / prefix caching / API 重叠）的功劳**。
   博客讲统一调度器那一节**一个性能数字都没有**。
   测试集：Llama 3.1 8B & 3.3 70B + ShareGPT；博客**未给** ITL / P999 / 显存数字。
2. **vLLM 官方调优文档 · Chunked Prefill**：两条收益 = (a) 改善 ITL（decode 优先）
   (b) 更好的 GPU 利用率（compute-bound prefill 与 memory-bound decode 同批）。
   调优律：budget 小 → ITL 好；budget 大 → TTFT 好；**「For optimal throughput we recommend
   `max_num_batched_tokens` > 8192」**（= chunk 近乎关闭的区间）；
   **「If `max_num_batched_tokens` is the same as `max_model_len`, that's almost the equivalent to the
   V0 default scheduling policy」** ← 官方自己承认的退化边界，与我们 B-base/C5 实测逐字吻合。
3. **SARATHI / Sarathi-Serve（OSDI'24，chunked prefill 源头论文）**：主张是 **tail latency** ——
   消除数秒级 generation stall、显著降低 P99 TBT，明确 **「prioritizing TBT over TTFT」**，
   吞吐是「same or better」；**尾延迟 SLO 约束下的服务容量 2.6×/3.7×/5.6×**
   （Mistral-7B 单 A100 / Yi-34B 2×A100 / Falcon-180B PP）。chunking 自身在极端情况有 ~25% 开销。

## 逐维度判定
| 维度 | 官方主张 | 我们实测 | 判定 |
| :--- | :--- | :--- | :--- |
| 吞吐 | 1.7×（V1 vs V0，归因 CPU 开销） | stress 0.990× / ctrl 0.958× | **不吻合但不矛盾**：杠杆在不同层；且官方自陈吞吐最优是 budget>8192 |
| ITL / TBT 尾部 | 消除数秒 stall、P99 TBT 大降 | ITL max 5.16×/20.11×/14.46×；停顿步 main 480→V1 5，最长连续 40→5；main 40 步×55ms≈2.2s 对上 ITL max 1985ms | **强吻合**（现象/量级/指标选择全对） |
| GPU 利用率 | 混合批提高利用率 | 95.9%（显存控制器 96.3%） | 吻合 |
| TTFT | 小 budget 牺牲 TTFT 换 ITL | 1.00~1.04×（几乎不变） | **吻合且可算**：并发 8 条 decode 只吃 8/1024 = **0.78%** budget → 长场景 TTFT 35614→35477 ms（−0.39%） |
| budget ⇄ ITL/TTFT | 文档明写 budget 是总旋钮 | budget 效应 9.29×（V1）/10.40×（main）；同 budget 分支差 1.13~1.43× | **逐字吻合** |
| 步 P999 / 峰值显存 | **官方未主张** | 步 P999 V1 高 1.13~1.43×；显存同 budget 1.0000× | 不参与对照（SARATHI 的 uniform batch 是为 **PP 多卡消 bubble**，单卡无 bubble） |
| **SLO 下服务容量** | SARATHI 2.6×/3.7×/5.6× | **未测** | ⚠ **唯一真实缺口** |

## 唯一真实缺口（度量轴不同，非结论冲突）
SARATHI 的 2.6× 是「**给定 P99 TBT ≤ SLO，能扛多大请求速率**」，而 C1/C0 全是**固定工作量**口径
（ctrl 下两版 token 逐位相同）→ **结构上不可能测出容量差异**。
补法：泊松到达 + 扫 RPS → 画「RPS vs P99 ITL」→ 取 SLO 下最大 RPS，两版相除即可直接对标 2.6×。
预期（未实证）：两版吞吐几乎相同而 ITL 尾部差 5~20× → **严格 ITL SLO 下 V1 容量应显著更高，SLO 越松越接近**。

## 一个必须正视的不吻合：官方有、我们没有的机器
博客原文两处：「the dynamism in V1—such as **combining prefill and decode within the same batch**—
a flexible and high-performance attention kernel was essential. **FlashAttention 3** effectively
addresses this requirement」+「V1 introduces **piecewise CUDA graphs** to alleviate the limitations
of CUDA graphs」。
→ vLLM V1 让**混合批不必牺牲 graph 加速**（attention 走可变 FA3，其余段仍可 graph 捕获）；
nano-vllm 没有 → 混批 decode 落回通用分支，C3 实测多花 **+24.17 ms(D=1) / +11.76(D=16) / +5.77(D=32) / +2.70(D=64)**。
**这就是我们 V1 的隐藏税，也解释了我们是「每步更长」而非「每步更短」。**

## 一句话结论
**机制层面吻合得相当好，吞吐数字不吻合且本来就不该吻合。**
我们复现的是 vLLM V1 的**调度器那一半**（统一 token 预算 + decode 优先 + chunked prefill + 增量 KV），
兑现的正是官方文档与 SARATHI 给 chunked prefill 派的**尾延迟与 GPU 利用率**；
1.7× 来自**执行循环那一半**，那部分我们没做、在本仓（单进程离线批处理、无 API server/流式/分词热点）也无杠杆。

# 2026-10-15（续）· CUDA 图 × 混合批：C6/C6b 实测 + 对照文档 §2 改写

## 起因
用户问「vLLM V1 让混合批不必牺牲 CUDA graph 加速是如何做到的，我如何进行优化？」并要求把对照结果存成文档。

## 关键实测（新脚本 `c6_prefill_graph.py` / `c6b_bisect.py` / `run_c6b*.sh` / `c6_fig.py`）
1. **C6b 二分：整步是可以捕获的**。唯一阻塞 = `nanovllm/layers/embed_head.py:60`
   `last_indices = last_indices[context.need_logits]` —— **bool 掩码索引内部走 nonzero，要一次 D→H 计数同步**，
   捕获流里报 `CUDA error: operation not permitted when stream is capturing`。
   换成「捕获外预计算的固定长度 1D int64 gather 索引」(= vLLM 的 `logits_indices` + pad) → `full` 阶段 PASS。
   `--no-attn` / `--no-compile` 仍失败，只有换索引才过 ⇒ **与 attention、与 torch.compile 都无关**。
   注意：这行是用户自己「跳过采样」优化引入的。
2. **`cap_model` PASS** ⇒ **固定形状下 FA 2.8.3 的 varlen + block_table + triton store_kvcache 都能进图**。
   官方说「attention 非图安全」的前提是"同一张图服务多种形状"；按桶各录一张就没这个问题。
3. **C6 收益量化（10/10 形状全部捕获成功，同形状同 buffer）**：
   | 形状 | T | eager | graph | 省 |
   |---|---:|---:|---:|---:|
   | decode×1 | 1 | 24.63 | 5.85 | **18.78 (4.21×)** |
   | decode×8 | 8 | 27.43 | 9.30 | 18.12 (2.95×) |
   | chunk32 | 32 | 25.81 | 5.56 | **20.25 (4.64×)** |
   | decode×32 | 32 | 28.20 | 20.97 | 7.22 (1.34×) |
   | chunk1024 | 1024 | 40.36 | 39.83 | 0.53 (1.01×) |
   | chunk1024+pc | 1024 | 74.82 | 73.59 | 1.23 (1.02×) |
   | mix1024+16 | 1040 | 80.69 | 79.82 | 0.87 (1.01×) |
   | mix1024+32 | 1056 | 91.54 | 90.27 | **1.27 (1.01×)** |
   | mix1024+64 | 1088 | 111.41 | 111.11 | 0.31 (1.00×) |
   | chunk4096+pc | 4096 | 365.98 | 364.68 | 1.29 (1.00×) |
   ⇒ graph 省的是**固定开销 ≈ 19 ms/步**（与 T 无关），T≥1024 时被 GPU 计算（40~366 ms）完全掩盖 → **只剩 1%**。

## 结论修正（推翻旧结论）
- 旧 C3 的「混合步 decode 多花 5.77 ms」= **在 T=32 的小 T 区间**测的（把 D 条 decode 单独喂进通用分支），
  外推到 T≈1050 不成立。**"混合步牺牲 graph" 的真实代价 = 0.3~1.3 ms/步（1.00~1.02×）**。
- ⇒ **vLLM 的 piecewise CUDA graph 不为"长 prompt chunk 混合步"服务**，它服务官方文档点名的小模型/小 prompt
  （launch 主导的 T 区间）；**而那个区间我们已经吃到**（纯 decode 步整批走图）。
- ⇒ 步 P999「V1 高 1.13~1.43×」**不能归因给 graph**（那是"一步做的事更多"）。判据应用墙钟/吞吐/ITL。
- ⇒ **该抄的不是 piecewise**，而是**统一 attention 按 query 长度分组派发后端**：C3 里
  `t_d_generic−t_d_eager = 4.287 ms(D=32) = 74% 的税`，graph 只占 1.48 ms (26%)。

## 新踩的坑（工具链）
- **块表必须落在 `config.num_kvcache_blocks` 内**：Qwen3-0.6B（28 层/8 KV heads/128 dim/fp16）**每块 29.4 MB**，
  `gpu_memory_utilization=0.8` 时只有 **148 块**；构造测试批时块号越界 → `store_kvcache` 写飞 → illegal memory access。
- **直接调 `runner.model(...)` 必须包 `torch.inference_mode()`**：`activation`/`rotary_embedding`/`layernorm` 挂了
  `@torch.compile`，grad 模式下 AOT autograd 会在 `silu_and_mul` 的 inplace 上报错。
- **CUDA sticky error 污染上下文** → 每个捕获阶段必须独立进程。
- **`import torch._dynamo` 写在函数里会把 `torch` 变成函数局部名** → `UnboundLocalError`；要写 `import torch._dynamo as _dynamo`。
- WSL 循环变量坑再次确认：`wsl.exe -- bash -lc "for ... do ... done"` 里的 `$var` 会被吃掉 → **循环必须写进 .sh 文件**。
