### 学生的两个回答与纠正
- Q「600 token 的序列 block_table 长度」= 3 ✅
- Q「生成到 601 token 表会不会变长」= 学生答「不会」❌ → 实际会在 `len(seq) % block_size == 1` 时追加一块，本例是第 769 个 token 时变 4（`block_manager.can_append/may_append`）。
- Q「共享前缀时 block_table 是否相同」= 学生答「前几项相同」✅ → 补充：只有**填满的完整块**可共享，故 `can_allocate` 循环 `range(num_blocks-1)` 特意排除最后一块。

### 本轮讲清的时序
- `schedule()` 里 `if not seq.block_table:` = 全新序列或被抢占后的重跑；`else:` = chunked prefill 续跑（waiting[0] 只读不 popleft，跑完才出队）。
- 前缀命中：`can_allocate` 返回 num_cached_blocks → `allocate` 里已有块 ref_count+1 / 从 free 池取回 → `num_cached_tokens = cached*256` → prefill 只算剩余部分。
- 缓存**产生**在 `postprocess → hash_blocks`（块被填满的那一刻）；**消费**在 `schedule → can_allocate`。
- `deallocate` 不删 `hash_to_block_id`，只有 `_allocate_block` 复用时才删 → 冷启动后前缀缓存仍有效。
- 缓存命中时 prefill 要走 `flash_attn_varlen_func(..., block_table=...)` 分支（attention.py:65-66 `k, v = k_cache, v_cache`）。
- 短 prompt（<256 token）永远不可能有前缀缓存：`range(num_blocks-1)` 为空。

### 第 3 课：什么是 batch（学生提问）
- batch 定义：一次 step() 中被选中共同做一次 forward 的一组 Sequence，每轮临时挑选，不持久化。
- 两个上限：`max_num_batched_tokens=16384`（token 预算）与 `max_num_seqs=512`（序列数）；prefill 还要过 `can_allocate` 的显存检查。
- 反直觉点：prefill batch **不是 [B, L] 的 padded 二维张量**，而是 1D 扁平拼接 + `cu_seqlens_q/k` 边界数组（varlen）；decode batch 才是 [B, 1]。
- 三态讲解：Scheduler 侧是 list[Sequence] 对象 → prepare_prefill/prepare_decode 拼接 → GPU 上只剩 torch.Tensor。`model_runner.run()` 是这道边界墙。
- 举例：600-token prompt × 100 条，第一轮只能进 27 条（27×600=16200 ≤ 16384）。
