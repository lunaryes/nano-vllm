# nano-vllm 魔改方向技术文档

## 一、背景说明

nano-vllm 是一个约 1200 行的轻量级 vLLM 实现，保留了 PagedAttention、Prefix Caching、连续批处理、CUDA Graph 等核心推理优化机制，但在调度策略、显存管理、模型支持等方面做了教学级简化。以下魔改方向均已有开源实现可供参考，建议按优先级顺序推进。


## 二、魔改方向总览

| 优先级 | 魔改方向                           | 难度  | 参考项目                                 | 核心收益                               |
| :----: | :--------------------------------- | :---: | :--------------------------------------- | :------------------------------------- |
|   P0   | Swap 机制                          |  ⭐⭐   | chengy-sysu/nano-vllm-swap               | 长序列场景下避免昂贵的 Prefill 重算    |
|   P1   | vLLM V1 调度策略 + Chunked Prefill |  ⭐⭐⭐  | anjoj0/nano-vllm-v1                      | Decode 优先 + 混合批调度，改善生成延迟 |
|   P2   | Speculative Decoding               | ⭐⭐⭐⭐  | banfeb/nano-vLLM-MS2                     | 吞吐量提升约 40%                       |
|   P3   | MoE 模型支持                       |  ⭐⭐⭐  | CefBoud/nano-vllm / banfeb/nano-vLLM-MS2 | 支持 Qwen3-30B-A3B 等 MoE 模型         |
|   P4   | KV Cache 压缩                      | ⭐⭐⭐⭐  | TheToughCrane/nano-kvllm                 | 长文本场景降低显存占用，提升解码吞吐   |
|   P5   | 多 LoRA / 量化支持                 | ⭐⭐⭐⭐⭐ | 暂无 nano 版参考                         | 单卡多 Adapter 服务 / 降低显存占用     |


## 三、各方向详细说明

### P0：Swap 机制

**任务主旨**：当 GPU 显存不足时，将暂时不运行的序列的 KV Cache 从 GPU 显存换出到 CPU pinned memory，等显存充裕时再换回，替代原版 nano-vllm 的 Recompute（重计算）抢占策略。

**为什么优先做**：
- 改动量极小（约 100 行新增代码），风险可控
- 原版 nano-vllm 的 `__getstate__` / `__setstate__` 方法已经为序列化 Swap 预留了接口，可以直接复用
- vLLM V1 默认使用 Recompute，原因是“重计算开销不超过 Swap 延迟的 20%”，但这是在 **block size 较小**时的结论。当 block size 较大（如 64 以上）或序列很长时，Swap 反而更高效
- 在 7B+ 大模型、长序列场景下，Prefill 重算代价远高于 PCIe 拷贝，Swap 的优势会显著体现

**需要完成的任务**：

| 模块               | 改动内容                                                                       |
| :----------------- | :----------------------------------------------------------------------------- |
| `config.py`        | 新增 `cpu_swap_space_gb` 配置项（默认 4GB）                                    |
| `sequence.py`      | 新增 `SWAPPED` 状态和 `cpu_block_table` 字段                                   |
| `block_manager.py` | 新增 CPU block 空闲列表、`swap_out` / `swap_in` 方法                           |
| `scheduler.py`     | 新增 `swapped` 队列；`preempt` 时优先 Swap-out，CPU 满时 fallback 到 Recompute |
| `model_runner.py`  | 分配 CPU pinned KV Cache 张量，新增 `swap_blocks()` 同步拷贝方法               |
| `llm_engine.py`    | 传递 swap mappings 到 model runner                                             |

**参考实现**：`chengy-sysu/nano-vllm-swap`，以约 100 行新增代码实现。

**性能参考**（Qwen3-0.6B，128 请求，A100-40GB）：

| 场景                      | GPU blocks | CPU blocks | 吞吐量 (tok/s) |
| :------------------------ | :--------: | :--------: | :------------: |
| 正常 (0.9 GPU)            |    1217    |     0      |      1371      |
| Swap (0.12 GPU + 2GB CPU) |     94     |     73     |      509       |
| Recompute (0.12 GPU)      |     94     |     0      |      560       |

小模型上两者接近（0.91x），但大模型长序列场景下 Swap 优势显著。


### P1：vLLM V1 调度策略 + Chunked Prefill

**任务主旨**：将原版 nano-vllm 的 Prefill-First 互斥调度，重构为 vLLM V1 的 Decode-First 混合批调度策略——**先调度所有 Decode 请求，再用剩余 token 预算调度 Prefill，并对最后一个放不下的 Prefill 进行分块**。

**为什么第二做**：
- 这是 nano-vllm 在调度层面最核心的差距，直接影响用户体验（ITL）
- 已有完整参考实现 `anjoj0/nano-vllm-v1`，约 1200 行，复现了 vLLM V1 的调度策略
- 原版 nano-vllm 的 Chunked Prefill 是被动、受限的“伪分块”——仅在队首且空批次时触发，Prefill 与 Decode 互斥执行。而 vLLM V1 的 Chunked Prefill 是主动的、以 token 预算为核心、支持 Prefill 与 Decode 混合调度的完整机制

**需要完成的任务**：
- 重构 `scheduler.py`，实现 Decode-First 的 token 预算分配
- 实现 `schedule_v1`，在每个 step 中同时调度 Prefill 和 Decode
- 引入 `max_num_batched_tokens` 的全局预算管理，先分配给 Decode，剩余给 Prefill
- 实现“只允许队首 Prefill 分块”的保护逻辑，防止多个不完整 Prefill 挤占 Decode 算力
- 支持 `chunked_prefill=True` 的启动配置

**参考实现**：`anjoj0/nano-vllm-v1`，关键特性包括 Paged Attention、Prefix Caching、Chunked Prefill、Tensor Parallelism、Torch Compilation，以及完整的 vLLM V1 调度策略复现。


### P2：Speculative Decoding（推测解码）

**任务主旨**：用小模型（Draft Model）或 N-gram 提议器生成多个候选 token，大模型并行验证，从而加速生成。

**为什么第三做**：
- 性能提升最直观——在 Qwen3-0.6B 上吞吐量提升约 40.8%（1418 → 1996 tok/s）
- 已有完整参考实现 `banfeb/nano-vLLM-MS2`，实现了端到端的推测解码路径，使用 N-gram draft token 提议
- 技术成熟度较高，N-gram 提议器使用 prompt lookup + Numba 加速，对大 batch 有自适应线程控制

**需要完成的任务**：
- 实现 Draft Model 或 N-gram Proposer，生成候选 token 序列
- 在 `model_runner.py` 中实现 `run_speculative_decode` 路径
- 实现并行验证逻辑：主模型对候选 token 一次性计算 logits，逐一验证
- 维护两套 KV Cache（Draft Model 和主模型），通过 `ModelRunner` 协调
- 保持 CUDA Graph 兼容性，batch sizes 列表需覆盖推测解码场景

**参考实现**：`banfeb/nano-vLLM-MS2` 和 `limei1221/nano-vllm-speculative-decoding`。


### P3：MoE 模型支持

**任务主旨**：在 nano-vllm 推理流水线中支持 Qwen3-MoE 等混合专家模型，包含基于 router 的 top-k expert 选择和融合专家计算。

**为什么第四做**：
- MoE 模型（如 Qwen3-30B-A3B）在推理时只激活部分参数，能以较低显存提供更大模型能力
- 改动集中在模型定义层，调度器、KV Cache、CUDA Graph 等核心机制**保持模型无关**，改动范围可控
- 参考项目 `CefBoud/nano-vllm` 通过 `hf_config.model_type` 自动选择模型类（`qwen3` vs `qwen3_moe`），改动清晰

**需要完成的任务**：
- 新增 `qwen3_moe.py`，实现 Sparse MoE 块替换 Dense MLP
- 实现 `moe_align_block_size` 等数据依赖的 token 排序逻辑
- 实现 router 的 top-k expert 选择与融合专家计算
- **注意**：MoE 模型**必须强制使用 Eager 模式**，CUDA Graph 不兼容，因为 MoE 的 token 路由是数据依赖的，每步变化，且排序函数使用 `.item()` 调用会强制 CPU-GPU 同步
- 在 `model_runner.py` 中设置 `self.enforce_eager = True`（MoE 模式）

**参考实现**：`CefBoud/nano-vllm`（commit e9c144e）和 `banfeb/nano-vLLM-MS2`（同时支持 MoE 和 Speculative Decoding）。

**性能参考**（Qwen3-MoE，RTX 3090，256 请求）：

| 引擎         | 输出 tokens | 时间 (s) | 吞吐量 (tok/s) |
| :----------- | :---------: | :------: | :------------: |
| vLLM         |   133,966   |   5.53   |     24,242     |
| Nano-vLLM-MS |   133,966   |   6.37   |     23,214     |

Nano 实现与 vLLM 性能接近（约 96%），验证了 MoE 路径的正确性。


### P4：KV Cache 压缩

**任务主旨**：当序列长度达到阈值 S 时，从 S 个 token 中选择 R 个“重要 token”的 KV，重组为新的 KV Cache，后续 decode 基于压缩缓存继续执行。

**为什么第五做**：
- 长文本推理时显存占用大幅降低，解码吞吐提升
- 改动量较小（约 100 行新增代码 + 2 个新文件），保持 nano-vllm 源代码布局基本不变
- **但难点在于必须兼容 PagedAttention 的 block 映射**（slot_mapping / block_tables / context_lens），压缩后需要做物理内存紧凑（compact），否则会出现碎片与无效槽位访问

**需要完成的任务**：
- 新增 `layers/compress_utils.py` 和 `layers/CompressMethod.py`
- 实现 `KVCacheCompress` 逻辑，在 Attention forward 中插入压缩步骤
- 实现压缩后 KV Cache 的物理内存紧凑（block 重组）
- 在 `scheduler.postprocess` 中根据 `compression_events` 更新序列元数据并释放多余 blocks
- 确保 TP（Tensor Parallelism）下各 rank 的元数据同步一致

**参考实现**：`TheToughCrane/nano-kvllm`，采用 Decode-only 压缩策略（Prefill 不压缩），先聚焦 decode 关键路径。


### P5：多 LoRA / 量化支持

**任务主旨**：在单卡上同时服务多个 LoRA Adapter（配合基座模型），或集成 AWQ / GPTQ / FP8 等量化方案降低显存占用。

**为什么最后做**：
- **难度最高**：多 LoRA 需要修改模型加载逻辑、Attention 和 MLP 层的前向计算（插入 LoRA 旁路），涉及面广
- 量化支持需要对模型权重进行后训练量化或加载预量化权重，涉及精度验证和 Kernel 适配
- 目前没有 nano-vllm 版本的开源参考实现，需要从 vLLM 原版移植

**需要完成的任务**：
- **多 LoRA**：模型加载时支持动态加载/卸载 LoRA 权重；Attention 和 MLP 层增加 LoRA 旁路计算；`SamplingParams` 中增加 LoRA 选择参数
- **量化**：集成 AWQ / GPTQ 权重加载；适配量化后的 Linear 层 Kernel；验证量化对生成质量的影响


## 四、优先级排序理由

1. **Swap 机制排第一**：改动最小（~100 行），风险最低，且原版预留的 `__getstate__` / `__setstate__` 接口可以直接复用。先做这个可以快速建立信心，同时为后续更复杂的改动打下基础。

2. **vLLM V1 调度排第二**：调度策略是推理引擎的核心，直接影响生成延迟和吞吐量。已有完整参考实现，但需要重构 `scheduler.py` 的核心逻辑，复杂度中等。

3. **Speculative Decoding 排第三**：性能收益最直观（~40% 吞吐提升），但需要维护双模型和双 KV Cache，架构改动较大，建议在前两步稳定后再推进。

4. **MoE 排第四**：改动集中在模型定义层，调度器保持模型无关。但 MoE 强制 Eager 模式会牺牲 CUDA Graph 的 Decode 性能，需要在收益和代价之间权衡。

5. **KV Cache 压缩排第五**：显存收益明确，但与 PagedAttention 的兼容性是最大难点。压缩后的 block 重组和物理内存紧凑需要精细实现，否则容易引入越界访问和碎片问题。

6. **多 LoRA / 量化排最后**：难度最高，且缺少 nano 版参考实现。建议在核心推理链路（调度、Swap、推测解码）稳定后再考虑。
